# Resistance 3 — native PC port/recomp (work in progress)

A static recompilation of the PS3 game *Resistance 3* into a native Windows program. No emulation of the CPU: the game's PowerPC and SPU code is translated to C/C++ and compiled for your PC. Graphics go through RPCS3's Vulkan renderer, with NVIDIA DLSS / AMD FSR upscaling, 60 fps, keyboard and mouse controls, and higher resolutions.

> ⚠️ **Not Perfect.** I have only tested it **on my PC** (Ryzen 5 5600X, GeForce RTX 5070, 32 GB RAM, Windows 11, 1080p screen) and haven't beaten the game. Only the intro and the opening Haven level have been played; past that it's untested, so things could go wrong. Some crashes or freezes may happen.

> **No game files and no translated game code are distributed, in this repository or in the installer.** You need your own copy of the game. Setup decrypts its program on your PC, translates it into C/C++ and builds the game there; the generated code and the built game never leave your PC, and no prebuilt game program is released. The repository holds the port's own code plus the small references it needs to find its place in the game's program: function addresses, patch values and short context lines from the generated code (`tools/hooks/` and `project/r3_patches.cpp`).

## What you need

- A PC running Windows 10 or 11 (64-bit).
- A CPU with AVX2: Intel 4th gen or newer, or any AMD Ryzen. Older CPUs get the slower variant without AVX2 (`build_baseline\`, built by setup); its minimum is SSE4.1 (Intel Core 2 Penryn / 45 nm or newer, AMD Bulldozer / FX or newer). On a CPU below that, the game says the processor is below the minimum (SSE4.1) and exits; setup skips the variant without AVX2 only when Windows reports SSE4.1 as missing (older Windows 10 versions can't tell, and then it is built as usual).
- A Vulkan 1.3 GPU. DLSS needs a GeForce RTX card; everything else (including FSR) works on AMD, NVIDIA and Intel. Only tested on NVIDIA so far.
- Your own dump of **Resistance 3, US disc (BCUS98176), version 1.00**. This is the folder that contains `PS3_GAME`, the same kind of folder RPCS3 uses. Other regions and patched versions are not supported yet.
- About 50 GB of free disk space: ~37 GB for the game files and the rest for the build tools and the build.
- An internet connection for the setup.

## Install

**Quick install (recommended):**

1. Download the release zip from the Releases page and unzip all of it to a folder with no spaces in the path, for example `C:\Games\Resistance3Port`.
2. Run **`Setup.exe`** in that folder. (It is not code-signed: if Windows says *"Windows protected your PC"*, click **More info → Run anyway**.)
3. Pick your game: **ISO...** or **Folder...**. Setup checks the copy at once and says what to do if it can't be used (see *If your game copy is not accepted* below).
4. Click **Install** and wait. Setup lists the build tools that are missing, says what each one is for and where it comes from, and asks before installing them (system-wide with one administrator prompt, or, experimental, portable inside the port folder; [details](docs/INSTALL.md#build-tools)). Then it copies your game files, builds the game with as many parallel jobs as your RAM allows, adds Start-menu and desktop shortcuts and starts the launcher. It shows the progress and the time left. If it stops (error, sleep, power cut), run `Setup.exe` again and click **Resume**.

The release contains no game code: the game is always built from your own copy. Requirements, disk space, build times, uninstalling and troubleshooting (SmartScreen, antivirus, low RAM, no winget): [docs/INSTALL.md](docs/INSTALL.md).

### Manual install (advanced)

**With the Inno installer** (if a `-Setup-<version>.exe` is on the Releases page): download `Resistance3Port-Setup-<version>.exe` from the Releases page and run it. It installs the port (default `C:\Games\Resistance3Port`), adds Start-menu and desktop shortcuts, and asks for your game. It lists the copies it finds on the PC (common folders and RPCS3's game list); you can also type or paste a path, or use the **ISO...** / **Folder...** buttons. It checks the copy before going on and says what is wrong and what to do if it can't be used (see *If your game copy is not accepted* below). At the end it opens **Setup**, the window with the progress bar, with your game already filled in: click **Install** there (step 2 below). The installer contains only the port; the game files always come from your own copy. Use a decrypted ISO or a game folder (the same kind RPCS3 uses). Tick **Portable mode** to keep settings only in the install folder. The install folder can't contain spaces (the build tools need that): a folder with spaces handed to the installer before its folder page (RecompLauncher suggests `C:\Recomp Library\...`) is replaced with the previous install's folder or `C:\Games\Resistance3Port`. The Start-menu shortcut is named *Resistance 3 PC Port (Resistance3Port)* so RecompLauncher recognises the install (it matches two words of the shortcut's name; an update removes the old *Resistance 3 PC Port* shortcut, and the uninstall entry is unchanged). RecompLauncher then finds the game through that shortcut and reads `recomplauncher.json` in the install folder.

**By hand:**

1. Download this repository: click on Code at the top, then Download ZIP, then unzip it somewhere with no spaces in the path, for example `C:\Games\Resistance3Port`.
2. Double-click **`Setup.bat`**. It will:
   - list the free build tools that are missing (Visual Studio 2022 Build Tools, LLVM, CMake, Ninja, Python, Git), what each is for and where it comes from, and ask first: **S** installs them system-wide with `winget`, **P** puts them only into `tools_cache\` in the port folder (experimental), **N** stops. `Setup.bat -RemoveTools` removes what Setup installed again ([docs/INSTALL.md](docs/INSTALL.md#removing-the-build-tools));
   - look for your game (an ISO or a game folder), check it, then copy it into the port folder (or move a folder, if it's on the same drive);
   - decrypt the game's program file, using the application keys from RPCS3's public source code;
   - download RPCS3's source at a fixed version and apply this port's renderer patch (`ps3recomp/patches/r3-rpcs3.patch`);
   - generate the game code from your copy and build the game.

   The first run takes a while: tool installs plus a 20–60 minute build. At the end, Setup offers to put a "Resistance 3" shortcut to the launcher on your desktop.
3. Play with **`Launcher.exe`**. It detects your PC and recommends settings (**Auto-detect**), and has all the settings (display mode, resolution, frame rate, VSync, anti-aliasing, upscaling, texture filtering, sharpening, frame generation, controls, notifications, mods and updates) and the key bindings. See [Launcher](#launcher-settings).

You only need to run Setup again after downloading a newer version of the port; otherwise just use the launcher.

**Choosing the game in Setup.bat:** it lists the copies it found, numbered. Type a number, or type or paste the path of the ISO or game folder (you can also drag it into the window). **B** opens a file picker (Windows only). `Setup.bat -Game "<path>"` skips the question. The path can be an ISO, the game folder, or a file inside it. An ISO is opened by Windows, copied from and closed again; if Windows can't open it, Setup reads it directly.

### Setup FAQ

- **Why does the first setup take so long? Is it a one-time thing?** Mostly, yes. The first run installs the build tools (10-30 minutes, once per PC), copies your game (5-15 minutes) and then compiles the whole game from your copy. That compile is the long part: the generated game code is split into a few very large files, each needing up to 8 GB of RAM, so a PC can only compile as many of them at once as its RAM allows. Measured on a 12-thread desktop CPU: about 45-60 minutes with 32 GB of RAM, about 2 hours with 16 GB, 2-3 hours with 12 GB; slower CPUs, laptops on battery and antivirus scanning add to that. Setup prints its own estimate and the time each step took (in `logs\setup.log`).
- **Updates are much faster.** Unzip the new version **over your existing port folder** (overwrite the files) and run Setup again: the tools, your game copy, the generated code and the compiled files are reused and only what changed is rebuilt, usually in 5-20 minutes. Unzipping into a **new** folder starts the game copy and the build from scratch again (the tools are still reused). When an update changes the code generator, Setup notices it by itself and generates the game code again (10-25 minutes; the first update after 0.2.3 does this once). Generated files that come out the same keep their date, so only the files that really changed are compiled again.
- **Making the first build faster:** close browsers and games while it runs (free RAM = more files at once); put the port on an internal NTFS drive (not a USB/exFAT drive or a network drive); optionally exclude the port folder from Microsoft Defender's real-time scan (Windows Security, *Virus & threat protection > Manage settings > Exclusions > Add an exclusion > Folder*), which otherwise scans every file the build writes. Setup tells you if Defender is scanning the folder; it never adds the exclusion itself.
- **"fatal: not in a git directory" / "detected dubious ownership" while fetching RPCS3:** fixed in Setup after 0.2.0 (GitHub issue #5). It happened on exFAT/FAT32 drives (most external and USB drives), network drives and folders owned by another Windows account, where Git can't confirm the folder's owner. Update the port, or move it to an NTFS drive (for example `C:\Games\Resistance3Port`).
- **How much disk space does it take, and what can I delete?** A finished install is about 40 GB: your game copy (`gamefiles`, the largest part), the generated code (`recompiled`), the compiled files (`build*` folders) and the tools. Keep them all: the build folders are what makes updates fast. Setup no longer copies the disc's bonus videos (`PS3_CONTENT`) or system update (`PS3_UPDATE`), which the game never reads, and deletes them and its work folder (`build_regen`) after a successful build. At the end Setup prints how much each part takes; run `powershell -ExecutionPolicy Bypass -File tools\build_doctor.ps1 -DiskUsage` to see it again. It also points out folders Setup did not make, such as a second copy of the port left by unzipping an update into a subfolder. Your original ISO or game folder is not needed after Setup has finished.
- **"ninja: error: manifest 'build.ninja' still dirty after 100 tries" and other build errors:** the "still dirty" error came from files dated in the future (the release zip's time zone, or a PC clock that was set wrong), which made the build loop. Fixed in 0.2.2: every build now resets such dates first. If a build still fails, Setup shows the first error and tries once more with a fresh build configuration (the files already compiled are kept). It does the same after the port folder was moved. To do it by hand: `powershell -ExecutionPolicy Bypass -File tools\build_doctor.ps1 -ResetConfig`, then run `build.bat` or Setup. `-FirstError` shows the first error from `logs\build.log` / `logs\build_rpcs3.log`; include that line and `logs\setup.log` when reporting a problem.

### If your game copy is not accepted

The installer and Setup check the copy before copying anything. The supported version is **Resistance 3 (US disc, BCUS98176)**, about 34.6 GB.

| Message | What to do |
|---|---|
| compressed archive (.zip, .7z, .rar) | Extract it first, then pick the ISO or folder inside. |
| PlayStation Store package (.pkg) / game update folder | Pick the disc copy. Game updates are not needed. |
| not &lt;game&gt; / from another region | Use the supported disc version listed above. |
| PlayStation Store version | Only the disc version is supported. |
| encrypted disc image / PARAM.SFO is not valid | Decrypt the ISO first (for example PS3Dec with the disc key from the `.dkey` file), or use a game folder from a PS3 or RPCS3. |
| program file was decrypted or replaced (plain ELF) | Use the original, unmodified files. Setup decrypts them itself. |
| files are missing / smaller than expected | The copy is incomplete. Copy or dump it again. |
| different from the known file (warning) | The copy may be modified. You can continue; Setup stops later if the decrypted program is not the supported version. |
| not enough free space | Free up space, or install on another drive. |

The checks run on your PC only. Nothing is uploaded.

**Updates:** the launcher checks this repository's Releases page once at start. The *Updates* option (Advanced page) picks what happens when a newer version is out: **Notify** (default) asks **Update now** / **Release page** / **Skip version**; **Auto-install** asks once, then updates; **Off** does not check (also `PORT_NO_UPDATE_CHECK=1`; `PORT_UPDATE_NOTIFY_ONLY=1` brings back the old notice that only opens the release page). *Update now* closes the launcher and runs `tools\update.ps1`: it downloads the release zip (checks its size and SHA-256), waits for the game to close, replaces the port's files, runs Setup in update mode (incremental: usually 5-20 minutes) and starts the launcher again. Your settings, key bindings you changed, saves, logs, game copy, generated code, build folders and shader caches are kept; a file is deleted only if an older release shipped it and you did not change it. If anything fails, the previous files are put back (log: `logs\update.log`; `tools\update.ps1 -Rollback` undoes an interrupted update, `-DryRun` only shows what would change). Git checkouts (`git pull`, then Setup) and copies installed by RecompLauncher (update them there) only get the notice. The installed version is in the `VERSION` file.

**Settings and controls** (`settings.ini`, `settings.bat`, `controls.txt`, `mouselook.cfg`) are also kept in `%USERPROFILE%\Saved Games\Resistance 3\config`. Missing files are restored from there when the launcher or game starts, so they survive reinstalling or updating the port. To keep everything in the port folder only, create an empty file named `portable.txt` next to `Launcher.exe` (the installer's *Portable mode* does this). Saves are still kept in the port folder (`gamedata`); the uninstaller asks before deleting it, and its default is to keep it.

**No console window:** the launcher starts the game without a console. The game's output goes to `logs\run.log`.

**First launch:** the game shows its own one-time setup screens and an autosave notice. Before the game starts, the launcher prepares the shader cache from your game files (a progress panel; **Skip for now** or Esc skips it), and the game then compiles every known shader behind a **Compiling shaders N / M** panel (see *Shader precompile*), so levels play without shader stutter from the first visit. Shaders are cached for later starts.

## Controls

Keyboard and mouse are supported out of the box: WASD move, Space jump, C/Ctrl crouch, Shift sprint, direct mouse look, Mouse1 fire, Mouse2 aim, Mouse3/F secondary fire, R reload, V/Mouse4 melee, G/Mouse5 grenade, 1/2 grenade type, Q / wheel weapon select, E use, Esc pause, Tab select, F8 releases the mouse. Controllers work too. All keyboard and mouse bindings can be changed in the launcher (Controls page, two keys per action; saved in `controls.txt`).

**Button prompts follow the device you used last.** Touch the keyboard or mouse and every on-screen prompt shows your keys; press a button or move a stick on a controller and they switch to that controller's buttons. Switching is instant and works anywhere, mid-game or in a menu. With an Xbox / XInput controller (or any non-PlayStation pad) the prompts show Xbox buttons, drawn by the port as simple coloured letters (no copied artwork):

| PS3 | Xbox | PS3 | Xbox |
|---|---|---|---|
| Cross | A | L1 / R1 | LB / RB |
| Circle | B | L2 / R2 | LT / RT |
| Square | X | L3 / R3 | LS / RS (stick click) |
| Triangle | Y | Select / Start | View / Menu |
| D-pad | D-pad | Left / right stick | Left / right stick |

With the XInput backend (`PAD_BACKEND=xinput`), a Sony DualShock 3/4 or DualSense that is plugged in (detected by its USB/Bluetooth ID, used through DS4Windows / Steam Input as XInput) keeps the PlayStation symbols; with SDL3 (default) the prompts follow the controller type, see *Controllers (SDL3)* below. The launcher's **Controller button prompts** option forces Xbox or PlayStation.

Where the prompts are replaced: Resistance 3's menus and HUD are Scaleform (Flash) movies, and every button symbol in them, on every screen, is one of the game's 18 `img://iconN` button pictures. The port swaps those pictures for the device in use, which covers the title / "Press Start" screen, the main menu, the lobby and options, the pause menu, loading-screen tips, the HUD and tutorial hints. Text that names a button inside a sentence (tutorials, hints) uses a symbol character; on keyboard that is rewritten to the key's name. PlayStation Move pictures are left alone. Prompts name the game's default button layout; if you remap buttons in the game's own options, they still name the default ones. `R2_KEY_PROMPTS=0` turns all of this off (PS3 symbols always).

**Mouse look is direct:** raw mouse counts turn the camera's yaw and pitch each frame (× the launcher's sensitivity, with its invert option), not an emulated right stick: no acceleration, dead zone or speed cap. While aiming down sights the turn rate is scaled by the scope zoom (`R2_ZOOM_SENS`: 1 = default, 0 = no scaling, up to 2). Mouse movement made while the camera isn't yours (menus, pause, cutscenes) is dropped, so the view doesn't jump afterwards. The launcher's **Mouse aiming = Classic** switches back to stick emulation. The shooting-range tutorial's look test ("look at the top target, then the bottom one") reads the mouse direction correctly, so it no longer offers to invert vertical look to mouse players who looked the right way (`R3_ML_LOOK_TRACK=0` restores the game's stick-only test). The game has no mouse pointer in its menus; use the keyboard (arrows / Enter / Esc) or a controller. F8 frees the cursor.

**Aiming and sticks** (launcher, Controls page):

| Option | Values | Variable |
|---|---|---|
| Vertical mouse sensitivity | **Same as horizontal**, 50 %, 75 %, 125 %, 150 %, 200 % | `PAD_MOUSE_SENS_Y=<0.1..4>` (multiplies the up/down mouse speed, direct and classic mouse aiming) |

Unset / `auto`: off for the keyboard & mouse player, on with a controller (in split-screen only the keyboard & mouse player loses it); `on`: always, as on PS3; `off`: never. Also in game (F9, and Options > PC Controls & HUD), where a change takes effect at once. Enemies aim as before |
| Stick deadzone | **Default** (XInput standard, per axis), Small 8 %, Medium 15 %, Large 25 %, Very large 35 % | `PAD_DEADZONE=<0..0.9>` (radial) |

All of these are also in game (**F9**, *More PC Options*) and apply at once. The crouch / sprint conversion assumes the game's own behaviour of those buttons, which was not verified in game; leave them on *As the game* if crouching or sprinting misbehaves.

**Controllers (SDL3).** The port reads controllers through SDL3 (built in, no extra DLL): Xbox, DualShock 4, DualSense, DualShock 3 (with its Windows driver), Switch Pro and Joy-Con work directly, over USB or Bluetooth. **DSX, DS4Windows and Steam Input are not needed**, and work best closed: they can hide the real controller from other programs (HidHide) and show only their virtual Xbox pad. If they run anyway and the port sees both the real controller and the tool's virtual copy, the copy is recognised by its mirrored input and ignored, so it doesn't become a ghost player 2 (with local co-op off, the default, a second controller never becomes player 2 anyway). Controllers can be plugged in and out at any time, no restart, up to 8. Rumble works on every pad that has it (DualSense included), and a DualShock 4 / DualSense light bar shows the player's colour (player 1 blue, player 2 red). If SDL3 can't start, the port falls back to XInput automatically (`logs\run.log` shows `[cellPad] controllers: SDL3` or `SDL3 could not start`; a build made without SDL3 says `controllers: XInput only`). If a controller isn't seen, `logs\run.log` lists every controller SDL3 found (`[pad-sdl3] controller 1: ...`), controllers it can't use, and notes when HidHide or a Steam setting may be hiding one.

**Button prompts by controller type:** with *Controller button prompts = Auto*, a PlayStation pad (DualShock 3/4, DualSense) shows PlayStation symbols and an Xbox or other pad shows Xbox letters. Switch controllers are read by button position (the bottom button is Cross); with *Nintendo button layout = Nintendo style* A (right) confirms and B cancels as on a Switch, and the prompts show the Xbox-style letters. Under Steam Input the real controller type is used when SDL reports it; otherwise set the prompts by hand.

**Gyro aiming** (DualShock 4, DualSense, Switch Pro, Joy-Con; off by default): turning the controller turns the view, added directly to the camera like the mouse (smooth, not limited by the stick). *While aiming* only uses it with the Aim button (L1 / LB) held. Leave the controller still for about a second after it connects so the resting drift is calibrated. In split-screen co-op each player's gyro moves only their own view (as a right-stick input, like the second player's mouse).

| Option (launcher Controls page / in game *More PC Options*) | Values | Variable |
|---|---|---|
| Controller support | **SDL3**, XInput | `PAD_BACKEND=sdl3\|xinput` (restart). `sdl2` is accepted and uses SDL3 |
| Gyro aiming | **Off**, On, While aiming | `PAD_GYRO=0\|1\|aim` |
| Gyro sensitivity | **2x**, 0.5x-6x | `PAD_GYRO_SENS=<0.05..20>` (view degrees per controller degree) |
| Gyro vertical | **Normal**, Inverted | `PAD_GYRO_INVERT_Y=1` (on top of the game's own invert setting) |

| Vibration | **100 %**, 75 %, 50 %, 25 %, Off | `PAD_RUMBLE=<0..100>` (`off` = 0): both motors scaled; Off also tells the game rumble is off (system setting). Also in the game's Options (*PC SETTINGS*) |
| Confirm button | **Cross**, Circle | `PS3_ENTER_BUTTON=circle`: the PS3 system setting the game reads at start (Japanese layout: Circle accepts, Cross goes back). Keyboard Enter / Esc / Backspace keep meaning confirm / back in menus. Restart; a menu that hard-codes its buttons ignores it |

With `PAD_BACKEND=xinput` the old behaviour returns: XInput only (up to four), PlayStation pads through DS4Windows / Steam Input, no gyro or light bar.

## Local co-op

Two players on one PC, split-screen, as on PS3. No PSN account is needed: the port provides a second local user.

**Starting it:** in the launcher, Controls page, set **Local co-op (split-screen)** to **On** (it is off by default, so a second controller, or a virtual copy of your controller made by DSX / DS4Windows / Steam Input, can't start split-screen by itself). Plug in two controllers (or one, with *Player 2 uses keyboard and mouse*). Main menu → **Campaign** → the co-op / split-screen option. On the lobby screen, press **START on the second controller** (or Enter / Esc on the keyboard for a keyboard player 2): on PS3 this opens the "select a user" box; the port answers it at once with a local user named **Player 2**, and player 2 is in. Start the chapter and the screen splits.

Resistance 3 counts at most two local players, ignores PlayStation Move pads, and won't let one user join twice (so player 2 is always the second local user).

**Who is who:**

- With local co-op off (the default): one player. Player 1 = the keyboard and mouse plus **the controller you used last**: pick up any connected controller and press a button, and it takes over. The game never sees a second controller.
- With local co-op on: player 1 = the keyboard and mouse plus the first controller found.
- Player 2 = the next controller. A controller keeps its player while it stays plugged in. A controller plugged in later takes the lowest free player; when one is unplugged, its player has no input until it is plugged back.
- With two local players the direct mouse look is off. The mouse then moves the keyboard player's view like a right stick (it would otherwise turn both heroes).

**Options** (launcher, Controls page; or `settings.bat`):

| Option | Values | Variable |
|---|---|---|
| Local co-op (split-screen) | **Off**, On | `PAD_COOP=1`: a second controller can join as player 2. Off (`PAD_COOP=0` or unset): the game sees only player 1, and extra controllers (or duplicate virtual pads from DSX / Steam Input / DS4Windows) can't join. *Player 2 controller* and *Player 2 uses keyboard and mouse* apply when it is On (outside the launcher, with `PAD_COOP` not set at all, setting `PAD_P2_CONTROLLER` or `PAD_P2_KEYBOARD` turns it on) |
| Player 1 controller | **Automatic**, Controller 1-8 | `PAD_P1_CONTROLLER=<1..8>`: the controller that is player 1 (SDL3: in the order they were connected; XInput: 1-4, Windows' XInput order). Automatic = the controller used last (co-op off) or the first one found (co-op on) |
| Player 2 controller | **Automatic**, Controller 1-8 | `PAD_P2_CONTROLLER=<1..8>`: the controller that is player 2 (numbered as above) |
| Player 2 uses keyboard and mouse | **Off**, On | `PAD_P2_KEYBOARD=1`: player 1 = the first controller only, player 2 = keyboard and mouse |
| (no launcher option) | **2** | `PS3_LOCAL_USERS=<1..4>`: local users the game sees. `1` = player 2 can't sign in. `PS3_USER2_NAME=<name>` renames player 2 |

`logs\run.log` shows which controller each player got (`[cellPad] player 2 <- controller 2`) and when the game counts two local players (`[coop] local players: 2`).

**Known limits:** Player 2's progress and settings are not saved separately (as on PS3 for a guest player). If you use NVIDIA DLSS, it may not work right in split-screen. Turn it off (or use FSR / no upscaler) for co-op if the image smears or one half looks wrong.

## Online (experimental)

Off by default; nothing here touches the network unless you turn it on. This is groundwork, not working online play: see the limits below.

**Turning it on:** launcher, Controls page → **Online (experimental)** → On (or `set PORT_ONLINE=1`). Copy `online.ini.example` to `online.ini` next to `run.bat` and put in **your own** RPCN account (make one with RPCS3 first; the port never creates accounts). `online.ini` is ignored by git; never share it.

What it does with `PORT_ONLINE=1`:

- Turns on real sockets for the game (`PS3_NET_ONLINE=1`).
- With `rpcn_user` and `rpcn_password` set, the game is told it is signed in, as that RPCN name. When the game asks for a sign-in ticket, the port connects to `rpcn_host` (TLS, port 31313), logs in and gets the ticket from RPCN, as RPCS3 does.
- Sends the game's server lookups (`gethostbyname`) to `host.<name> = <ip>` entries first, then to the `dns =` server (for community revival servers that are reached through a custom DNS), then to Windows' DNS.

| Variable / `online.ini` key | Meaning |
|---|---|
| `PORT_ONLINE=1` | Turn it on (default off) |
| `PORT_ONLINE_CONFIG=<path>` | Read another file instead of `online.ini` |
| `PORT_ONLINE_PROBE=1` | At start-up, only check that `rpcn_host` answers (TLS + server version; no login). The result is in `logs\run.log` (`[online] probe`) |
| `rpcn_host`, `rpcn_user`, `rpcn_password`, `rpcn_token` | RPCN server (default port 31313) and your account. The password and token are never written to the log |
| `dns` | IPv4 address of a DNS server for the game's lookups |
| `host.<name>` | Fixed IPv4 address for one host name |

`logs\run.log` lines start with `[online]` (config read, sign-in state, ticket requests) and `[sys_net] gethostbyname` (each server name the game looks up and where it went).
**Limits:** Resistance 3's official servers are shut down and there is no known community server, so there is nothing to play online against yet. The port only signs in and fetches tickets; matchmaking, voice and NAT are untested and some online functions are still stubs.

## PC features

- **PC menu:** press **F10**, hold **Esc** for 1 s (`R3_ESC_HOLD_MENU=0` turns this off), or hold **View + Menu** (Select + Start) on a controller for 1.5 s, for a small overlay menu: **Resume**, **PC Options** and **Quit to Desktop**. The game is paused while it is open. *PC Options* changes, live: frame rate, upscaler (DLSS / FSR 3.1 / off; applies at the next start), mouse sensitivity, field of view and controller prompts (Auto / Keyboard keys / Xbox / PlayStation). Each change is saved where the launcher keeps it (`settings.ini` + `settings.bat`, `controls.txt`). Arrow keys / D-pad move, Enter / A select, Esc / B back. There is no on-screen F10 hint: the game's own Options screen carries the PC settings (next item). `R2_MENU_PC=0` turns the menu off (F10 / View+Menu then go straight to the quit box).
- **PC settings in the game's own Options menu:** the game's Options screen (main menu and pause menu) gets one tab per PC category, between VISUAL and MOVE (main menu: between 3D and MOVE; both screens are built by the same game code, so one hook covers both, and the 3D / MOVE locks stay where the game put them) — the same categories, names and order as the R1 / R2 ports: **PC DISPLAY** (frame rate, field of view, aspect ratio, brightness, HDR), **PC GRAPHICS** (anti-aliasing / upscaler, upscaling, frame generation, Reflex), **PC EFFECTS** (depth of field, aim-down-sights blur and its approximation, motion blur, film grain, colour-blind filter), **PC CONTROLS & HUD** (mouse sensitivity, button prompts, vibration, crosshair / colour / size, hold to skip movies, skip unwatched movies), **PC AUDIO & LANGUAGE** (master volume, mono audio, language). Rows whose setting is missing from this build are left out. Up / down picks a category, accept / right opens it, back returns to the tab list, as with the game's own tabs. Left / right changes a value; it is saved and applied exactly like the F10 / F9 menus (same `settings.ini` / `settings.bat` entries, so the launcher and the overlay menus show the same values). Rows marked *(restart)* apply at the next start. The game's own CONTROLS / AUDIO / VISUAL tabs and its saved options are untouched: PC rows use ids the game ignores, and a change only makes the game redraw the list. The tab and its rows are added to the game's Flash menu at run time (`project/r3_menurows.cpp`; no game files changed); if the menu ever refuses the tabs, the rows go to the end of the CONTROLS tab instead, grouped under *--- PC DISPLAY ---* style headers (logged as `[menurows] ...`). `R3_MENU_ROWS=2` keeps that layout (rows at the end of CONTROLS), `R3_MENU_ROWS=0` turns them off; F10 / hold Esc always has every PC setting.
- **PC wording:** the game's text is adjusted where it talks about the console (rules in `project\r3_pctext.cpp`). In English: the epilepsy warning's "BEFORE USING SEE THE INSTRUCTION MANUAL INCLUDED WITH YOUR PS3™ SYSTEM FOR MORE DETAILS." → "STOP PLAYING AND CONSULT A DOCTOR IF YOU FEEL UNWELL.", "Press and hold the PS button to quit the application" → "Press F10 to quit the game", "Insufficient Hard Disk Drive space" → "Insufficient disk space", "Do not switch off the power when the HDD access indicator is flashing" → "Do not close the game while it is saving", "Logging into PlayStation®Network" → "Signing in to online services", "PlayStation®Network account" → "online account", "PlayStation®Store" → "online store", "USB keyboard" → "keyboard", and "wireless controller" → "controller". Other languages: "PLAYSTATION®3" / "PS3" → "PC", "PlayStation®Network" → "Online", "PlayStation®Store" → "Store", and the PS button in quit messages → F10. Credits, trademark lines and PlayStation Move / Eye messages are left as they are. Only the text in memory is changed (the game files aren't touched). `R3_PC_TEXT=0` turns it off (`R2_PC_TEXT` is still read when `R3_PC_TEXT` is unset).
- **Quit to desktop:** *Quit to Desktop* in the PC menu (or F10 / View + Menu with `R2_MENU_PC=0`). A small box asks *Quit to desktop?*: Enter / Space / A = yes, Esc / Backspace / B = no. While it is shown the game is paused and gets no input. On yes (and also when the window is closed with Alt+F4 or the X button) the port waits for a save in progress to finish (up to 15 s, "Saving..."), flushes open files and exits. The game's own menus have no Quit entry; adding one would mean patching the game's Flash menus without being able to test them, so the PC menu carries it instead.
- **Alt+Enter** switches between borderless fullscreen and windowed. **Alt+Tab** is safe in borderless and windowed mode.
- **Monitor** (launcher, Display › Screen): which screen the window opens on (`RSX_MONITOR=<n>`, 1-based in Windows' order; empty = primary).
- **Remember window position** (launcher, Display › Screen, F9; `RSX_WINDOW_REMEMBER`, default on, `0` = always centred): a windowed game reopens where you last left it, at that size (`window_pos.txt` in the game folder, written when a move / resize ends and on close, never in fullscreen). It is ignored when the window size or monitor setting changed, or when the spot is no longer on any screen.
- **When the game is in the background** (launcher): *Pause and mute* (default) freezes the game and silences it when the window loses focus; *Mute only*; *Keep running* (`R2_BACKGROUND=pause|mute|run`). On focus loss the cursor is always released and shown; it is also shown while the quit box is up or the game is paused this way, and captured/hidden again when you click back in.
- **Skip intro movies** (launcher, default on): the studio logo video and the opening movie are skipped, so the game starts at the title screen (`SKIP_INTRO=1`, set by `run.bat`; `SKIP_INTRO=0` to watch them).
- **Frame rate in menus** (launcher): caps the frame rate at 60 or 30 fps whenever you are not controlling your character (menus, loading screens, cutscenes); gameplay keeps the normal frame rate (`PORT_MENU_FPS=<fps>`, minimum 30; empty/0 = off, the default).
- **Screenshots:** **F12** or **PrtScn** saves `screenshots\R3_<date>_<time>.png` in the game folder (a short "Screenshot saved" note appears). The launcher's About page has **Open screenshots**.
- **Saves** are in the game folder: `gamedata\dev_hdd0\home\00000001\savedata\BCUS98176_SAVE_0` (game settings are saved there too, as on the PS3). The launcher's **Saves & tools** page backs them up and restores them (see *PC extras*). **Open save folder** (launcher, About) opens it. `PS3_GAMEDATA_ROOT=<dir>` moves the whole `gamedata` tree elsewhere (saves then go to `<dir>\dev_hdd0\home\00000001\savedata`). The port's own settings are `settings.ini` / `settings.bat` and `controls.txt` in the game folder.
- **Reset all to defaults** (launcher, About) resets display, graphics, PC options, keys and mouse (saves untouched). **Auto-detect** (Display, Graphics and Upscaling & Frame Gen pages) resets only display and graphics; **Restore default controls** only the controls.
- **Crash and hang reports:** if the game crashes, a minidump is written to `logs\crash\R3_<date>_<time>_crash.dmp` and a one-line summary is added to `logs\crash\crashes.txt`. If no game frame is drawn for 90 s while the game isn't paused, an `R3_<date>_<time>_hang.dmp` with every thread's state is written once per stall and the game keeps running. Send these with the session's log when reporting a problem. `R2_HANG_S=<seconds>` (≥ 10) changes the hang limit, `R2_CRASH_DUMPS=0` turns reports off, `R2_CRASH_DUMPS=full` writes full-memory dumps (large). **Freeze restart:** `run.bat` sets `FREEZE_RELAUNCH=900`: if the frame counter stops for 900 s (15 minutes) while the game isn't paused, every thread's stack and the SPU state go to `logs\freeze_<tick>_<n>.txt`, and the game restarts itself with the same command line (back to the main menu; your last save is kept). `set FREEZE_RELAUNCH=0` in `settings.bat` turns it off, another number changes the wait in seconds.
- **Frame-time report (stutter log):** the port records every present-to-present interval (lock-free, no per-frame allocation). At exit, and when a crash or hang report is written, it writes `logs\frametimes_<date>_<time>.txt`: average, 1% low, 0.1% low, worst frame, a histogram, the 20 worst frames with their time and clock time, and stalls of 1 s or more (loading screens, hangs; left out of the numbers). Game pauses (menu, unfocused window) are left out. The newest 10 files are kept; **Report a problem** includes the newest five (user name scrubbed). Press **Scroll Lock** while playing to flag a bad moment: a `[frametime] MARKER` line with the last 2 s of frame times goes to the log and to the file (F8 is the mouse-release key). `PORT_FRAMETIME=0` turns the recorder off; `PORT_FT_MARKER_KEY=scroll|pause|f1..f24|off` picks the marker key. If the recorder ran for over 60 s without seeing a frame, the log gets a `[frametime] WARNING: ... present hook ... is missing` line.
- **Renderer fatal errors:** if the RSX renderer thread hits a fatal error, the reason is printed to the console/log as `[rpcs3] thread '...' terminated due to fatal error: ...` (and to `logs\rpcs3_rsx.log`). The previous run's `rpcs3_rsx.log` is kept as `logs\rpcs3_rsx.prev.log`, so it survives one restart. A dead renderer thread looks like a hang (the game stops drawing but keeps running), so include these lines when reporting one.
- **Performance overlay:** **F3** shows or hides frame rate, frame time (average and worst) and, with the Compatible renderer, draws per frame and the RSX thread's time per draw, in a corner of the game window. Launcher *Performance overlay*: Off (F3 shows it, the default), On at start, Disabled (F3 does nothing) = `R2_OVERLAY` unset / `1` / `0`; `R2_OVERLAY_POS=tl|tr|bl|br` picks the corner (top left by default). It is drawn into the game's own image (`PORT_OSD`), so it also shows in exclusive fullscreen. While it is shown the renderer's counters are on (as with `R2_RSX_PROF=1`, without the log output).
- **Trophies as local achievements:** when the game awards a trophy the port shows a PS3-style pop-up: a dark rounded box near the top corner (opposite the F3 overlay) that slides in for about 6 s, with the trophy's own icon from `TROPHY.TRP` (a cup in the grade's colour if it can't be read) at the left, "You have earned a trophy." and the name below it (scaled to the window height; drawn into the game image, so it also shows in fullscreen, HDR included). Several unlocks queue. `PORT_TROPHY_STYLE=old` (or `R3_TROPHY_STYLE=old`; launcher *Trophy pop-up style: Classic*) brings back the older notification with the grade badge and description. `PORT_TROPHY_TEST=1` shows one sample pop-up per grade a few seconds after start-up, to check the look. It records it in `%USERPROFILE%\Saved Games\Resistance 3\trophies.json` (name, grade, date). The trophy list (59 trophies, comm id `NPWR01841`) is read at run time from your own game files (`gamefiles\PS3_GAME\TROPDIR\NPWR01841_00\TROPHY.TRP`); nothing of it ships with the port. The platinum trophy is awarded when every trophy it counts is unlocked. The runtime's own record stays in `gamedata\trophies\NPWR01841.json`. The launcher's **Trophies** page shows a summary at the top (earned / total, percentage, a progress bar and the count per grade), then every trophy with its icon from `TROPHY.TRP` (greyed until earned), name, description, grade and the date it was earned, newest first. Hidden trophies show as *Hidden trophy* until earned. It merges both records (a trophy counts if either has it; the earliest time wins), so the platinum the port awards also shows. Before anything is earned it says *Play the game to start earning trophies*. The page reads nothing until it is opened, re-reads only when those files change, and never writes to them. `R2_TROPHY_TOAST=0` (launcher *Trophy notifications: Off*) records them without the notification.
- **Mods folder:** launcher *Mods folder: On* (`R2_MODS=1`) loads replacement game files from the `mods` folder next to the game; `R2_MODS=<folder>` uses another folder. Each sub-folder is one mod laid out like the game's `PS3_GAME` folder: `mods\<mod>\USRDIR\...` replaces the same file under `gamefiles\PS3_GAME\USRDIR`. Names are matched without regard to case; when two mods replace the same file, the one whose folder name sorts last wins (or the lower one in `mods\order.txt`, written by the launcher's *Saves & tools › Mods* list, which can also turn mods off); folders starting with `_` are skipped (a quick way to disable one). Every replaced file is listed in `logs\run.log` as `[mods]` lines. Single members of a `.psarc` archive and single level assets (by tuid) can be replaced too: see [docs/MODDING.md](docs/MODDING.md).
- **Ultrawide (Hor+, untested in game):** launcher / F10 *Ultrawide / aspect ratio* (`R3_ULTRAWIDE=auto`, `21:9`, `32:9` or a ratio such as `2.39`; a change in F10 or the Options rows applies at once). The game still renders a 16:9 image, but the camera frustum setter (`func_00799EF0`) widens the horizontal field of view to the target aspect (vertical FOV kept), and the Compatible renderer stretches that image to the window, so nothing looks stretched and there are no side bars. Shadows and culling follow, because they are derived from the same frustum. Combine with `RSX_HUD_FIX=1` (launcher *Ultrawide HUD*) to keep the HUD at 16:9. The native renderers cannot stretch, so with them (developer option `R3_RENDERER_FORCE_NATIVE=1`) the setting is ignored: 16:9 with side bars and an `[aspect] WARNING` line in `logs\run.log`.
- These window features (F10, F3, F12, pause on focus loss, monitor choice) work with both renderers. The port's menus, overlay and notifications are drawn into the game's own image (`PORT_OSD`, default), so they also show in exclusive fullscreen; `PORT_OSD=layered` uses the old separate windows, which exclusive fullscreen hides. Exclusive fullscreen can still give black screenshots; borderless is recommended.

### PC extras

All of these are in the launcher (on the Display, Graphics, Upscaling & Frame Gen, Controls, Interface & Notifications and Advanced pages, see *All launcher options*, and the **Saves & tools** page) and most also in game: **F9**, or **F10 › More PC Options**. The in-game page writes the same `settings.ini` / `settings.bat` lines as the launcher. Rows marked *(next start)* apply after a restart; the rest apply at once. Code: `project\r3_pcextra.cpp` (game side), `project\launcher_extra.inc` (launcher), `ps3recomp\third_party\rpcs3\rpcs3\Emu\RSX\VK\VKR2PcExtras.cpp` (Vulkan HDR / colour-blind / Reflex). New switches use the `R3_` prefix.

- **Skip intro movies** — `SKIP_INTRO` (above, default on). The epilepsy / legal notice is a game screen that waits for a button and is not skipped (the code that sequences it was not located).
- **Key rebinding** — keyboard and mouse: launcher Controls page or in game *More PC Options › Key bindings* (Enter = press the new key, Esc = cancel; written to `controls.txt` and re-read at once). Controller: launcher *Controller buttons* or in game *More PC Options › Controller layout* — each Xbox button can act as another one (`PAD_MAP_<button>=<button>`, e.g. `PAD_MAP_A=B`), `PAD_SOUTHPAW=1` swaps the sticks. The remap is applied to the XInput state before the game sees it.
- **Automatic prompts** — `R2_PAD_GLYPHS=auto` (default): the prompts follow the last device used. Already in the port; listed for completeness.
- **Post-effect toggles** — `R3_FX_FILMGRAIN`, `R3_FX_DOF`, `R3_FX_ADS_BLUR` (aim-down-sights blur only), `R3_FX_MOTIONBLUR` (default `1` = the game's own look; `0` = off). Also in game (*More PC Options*, F9) and in the launcher; the in-game switch applies at once. Each frame the engine blends its post volumes and Lua `pfx_*` nodes into a per-view post block (0x12B3E80 + view × 0x230) and then calls one function per effect with a parameter struct. Each function returns early when its strength is zero, so the hooks in `tools/hooks/r3.json` zero only that strength before the function reads it, and the game takes its own "effect off" path:

  | Effect | Function | Field zeroed | Skip test in the game |
  |---|---|---|---|
  | Film grain | `func_00744A18` | p+0x08, grain intensity (block 0xEC) | ≤ 0 |
  | Camera motion blur | `func_007424F8` | p+0x14 (block 0xD8) | ≤ 0 |
  | Object (per-moby) motion blur | `func_00855A98` | p+0x0C, sample scale | < 0.01 |
  | Depth of field | `func_008557A8` | p+0x28 / p+0x38, near / far max blur (block 0xC4 / 0xD0) | both < 0.01 |

  Only the stack copy is changed, so turning an effect back on restores the level's exact values. The Lua `pfx_set_node_*` natives (registered at 0x8EA7E0 through `lis`/`addic` pairs, which is why a plain pointer search finds no references) feed the same block, so script-driven effects are covered too.
- **Colour-blind filter** — `R3_COLORBLIND=1|2|3` (protanopia / deuteranopia / tritanopia): daltonization in the final output pass (Compatible renderer). Applies at once. The filter decodes sRGB to linear light, daltonizes (ReShade *Daltonize* matrices: simulate the deficiency, shift the lost red/green error into green/blue), re-encodes, and runs before HDR encoding. Strength is fixed at full.
- **Extra crosshair** — `R3_CROSSHAIR=dot|cross`: a small marker at the window centre during play (hidden in menus, the PC menu and photo mode). **Crosshair colour** `R3_CROSSHAIR_COLOR` (`white` default, `green`, `yellow`, `cyan`, `red`, `pink`, `orange`) and **Crosshair size** `R3_CROSSHAIR_SIZE` (`small` default = 24 px, `medium`, `large`, `huge`, or a percentage 50-400) — always with a dark outline; live in F9 and in the launcher.
- **Window** — `RSX_RESIZABLE` (default on): the windowed-mode window has a sizing border and the swapchain follows the new size. `RSX_ALT_ENTER` (default on): Alt+Enter switches windowed ↔ borderless fullscreen.
- **Frame rate** — the cap is the port's frame limiter (`R2_FPS`, launcher *Frame rate*); there is only one limiter. Above 60 fps the game clock follows real time through the ported Unlock-FPS hooks (frame-time floor and game-clock clamp, see *RPCS3 patches*), so the game does not speed up; frame-counted logic was not audited frame by frame (as UnleashedRecomp did for its game), so treat 120 / 144 / Uncapped as less tested than 60.
- **NVIDIA Reflex** — `R3_REFLEX=1` (`2` = + Boost), opt-in, Compatible renderer, GeForce with `VK_NV_low_latency2`: low-latency mode plus the Reflex sleep at the start of each frame. It does not cap the frame rate; no latency markers are sent. Does nothing when the extension is missing.
- **Latency reduction** — `PORT_LATENCY=off|reflex|antilag|auto` (launcher: Upscaling & Frame Gen › *Latency reduction*, F9 too; unset = `R3_REFLEX` alone decides, as before). `reflex` turns NVIDIA Reflex on (Boost with `R3_REFLEX=2`); `antilag` = **AMD Anti-Lag 2** through `VK_AMD_anti_lag` (Radeon with a driver that exposes it): `vkAntiLagUpdateAMD` INPUT stage once per frame after the limiter and PRESENT stage around each present; `auto` = Reflex on NVIDIA, Anti-Lag 2 on AMD. With Reflex on, the Compatible renderer now also sends the **Reflex latency markers** (`vkSetLatencyMarkerNV`: SIMULATION_START/END, INPUT_SAMPLE at the first port-0 `cellPadGetData` of a frame, RENDERSUBMIT_START/END, PRESENT_START/END) so the driver and the NVIDIA overlay's PC latency see the frame; `R3_REFLEX_MARKERS=0` = sleep only (the old behaviour). Neither is used while frame generation is on (it has its own Reflex). Experimental.
- **DLSS Frame Generation** — `R3_DLSS_FG=2|3|4` (launcher: Upscaling & Frame Gen › *Frame Generation*; `0`/unset = Off), Compatible renderer, GeForce RTX 40 (2x) or RTX 50 (up to 4x Multi Frame Generation), Anti-aliasing = NVIDIA DLSS, setup's optional NVIDIA Streamline download. The GPU inserts 1-3 generated frames between the game's own (`ps3recomp\third_party\rpcs3\rpcs3\Emu\RSX\VK\VKR2FrameGen.cpp`, NVIDIA Streamline 2.14.16, manual hooking). Smoother motion when the CPU is the limit; adds a little input lag, so Reflex is switched on with it (Streamline drives Reflex while FG is set up; `R3_REFLEX=2` = Boost). The frame-rate setting caps the game's own frames; the Reflex cap keeps rendered × multiplier under the refresh rate. The HUD is split from the scene in the renderer (HUD draws after the 3D pass go to a UI layer that is composited after generation), so HUD text does not warp; when a frame's HUD can't be separated cleanly it is passed through untouched. FG pauses in menus, movies, loading screens, split-screen, while the game is paused and on scRGB HDR, and turns itself off (one `[fg-vk] frame generation off: ...` log line) on other GPUs, without the DLLs, or with FSR / XeSS / no AA. Debug: `R3_DLSS_FG_HUD=0` (no HUD split), `R3_DLSS_FG_HUD_DEBUG=1` (show the HUD-less image), `R3_DLSS_FG_MENU_OFF=0`, `R3_DLSS_FG_GAP=0` (warm up again after every scene-less frame), `R3_DLSS_FG_CAP=0`, `R3_DLSS_FG_YFLIP=0`, `R3_DLSS_FG_DEBUG=1`. With a fixed-refresh display and no G-Sync, vsync is replaced by the Reflex cap and may tear. If Streamline fails or faults while it sets up the Vulkan device (driver or plugin problem), DLSS-G is dropped for that run with a `[fg-vk]` log line and, with `R3_FG_BACKEND=auto`, FSR 3 2x takes over instead of the game crashing. Streamline plugins: the matched 2.14.16 set next to the exe is used and NVIDIA's over-the-air plugin updates are off (`R3_DLSS_FG_OTA=1` turns them back on); an NVIDIA App / driver *DLSS override* can still swap in the driver's own plugin builds (`ProgramData\NVIDIA\NGX\models\sl_*_override_*`, logged once), and `R3_DLSS_FG_OVERRIDE_PLUGINS=0` refuses DLSS-G in that case (auto: FSR 3). Diagnostics: `R3_FG_DIAG=1` logs a `[fg-diag]` line per second (real vs generated presents, generated frames Streamline did not present, frame-generation resets by cause with the held camera-cut values, pauses, a real present-interval histogram with spikes and pace jumps, Reflex sleep, DWM refresh / composition rate) and **Pause** (`R3_FG_DIAG_KEY=pause|scroll|f1..f24|none`) appends the previous 30 and next `R3_FG_DIAG_FRAMES` (default 120) presents frame by frame to `logs\fgdiag.txt`; `R3_FG_DIAG=2` also starts that dump by itself on a suspect event (at most `R3_FG_DIAG_AUTO_MAX`, default 10, 20 s apart). `R3_FG_DIAG=3` (the test launchers' setting) keeps the per-second lines and records every present, with the dump's columns, to `logs\fgdiag.txt` until the game closes (the previous session's file becomes `fgdiag_prev.txt`; if that rename fails, e.g. the old file is open in another program, it is left alone and this session writes `fgdiag_<pid>.txt`, named in `run.log`): resets with their reason, pauses, undelivered generated frames, DLSS-G status changes and spikes are `--- ... ---` lines in the stream, a `# second` line follows each second, and **Pause** writes a `--- user marker ---` line (press it when a duplicate frame or ghosting shows). One writer thread empties a preallocated queue every 250 ms (no file I/O on the present thread; a full queue drops rows, counted in the file and `run.log`); about 0.6 MB per minute at 60 rendered fps; the file stops at `R3_FG_DIAG_MAX_MB` (default 512). Without it, a `[fg-vk] frame generation in 10 s: N resets (...)` line follows the 10 s DLSS-G status line when resets, undelivered generated frames or pauses happened.
- **FSR 3 Frame Generation (fallback)** — `R3_DLSS_FG=fsr3` (launcher: *Frame Generation* › *FSR 3 2x*, listed on GPUs that are not RTX 40/50), or `R3_FG_BACKEND=auto|dlss|fsr3` (auto = default: DLSS-G first, then FSR 3 2x when DLSS-G is unavailable; `dlss` = DLSS-G only; `fsr3` = FSR 3 only, also on RTX cards). AMD FidelityFX frame interpolation (FidelityFX API 1.1.4, `tools\ffx_vk\amd_fidelityfx_vk.dll`, MIT, shipped with the port) on any Vulkan GPU with a spare present-capable queue and timeline semaphores; 2x only. Needs Anti-aliasing = FSR, DLSS or XeSS (for depth and motion vectors) and SDR or HDR10 output. Uses the same inputs, HUD split (the HUD-less scene goes to interpolation, the HUD layer is composited on every shown frame), camera-cut resets and pause rules as DLSS-G. No Reflex while it is selected (FidelityFX's swapchain has no low-latency mode), so it adds a little more input lag than DLSS-G; the game's frame cap still applies to its own frames and FSR 3 paces the generated ones. Turning it on or off mid-game waits for the GPU once (a short hitch). HDR10 works on the usual A2B10G10R10 swapchain; a driver that only offers A2R10G10B10 for HDR10, and scRGB HDR, keep FG paused. Debug: `R3_DLSS_FG_DEBUG=2` (FidelityFX tear lines and reset markers); the HUD switches above apply too. Off reasons are logged as `[fg-vk] ...` lines.
- **HDR output** — `R3_HDR=auto` (HDR10 when Windows HDR is on for the game's monitor, else SDR), `R3_HDR=1` (HDR10 / PQ) or `R3_HDR=scrgb` (FP16 linear), opt-in, Compatible renderer, Windows HDR must be on. The final pass converts the SDR image to linear and scales SDR white to `R3_HDR_PAPER` nits (default 203), then encodes PQ or scRGB; `R3_HDR_PEAK` (default 1000) is sent as `VK_EXT_hdr_metadata` and caps highlights. Falls back to SDR when the display/driver has no HDR surface format (logged). The F3 overlay, PC menu and screenshots stay SDR.
- **Hold to skip movies** — `R3_CUTSCENE_SKIP` (default on): hold Space / Enter / A / Menu for 1 s while a pre-rendered movie plays and the port presses the game's own skip button. Loading-screen movies and in-engine cutscenes are not skipped (not safe). A *Hold Space / A to skip* notification when a movie starts: launcher *Show cutscene skip hint* (`PORT_SKIP_HINT`, or `R3_SKIP_HINT`) **Auto** (default, unset) shows it when Skip unwatched movies is on, since every story movie can then be skipped; *On* (`1`) always, *Off* (`0`) never. Holding skips either way. **Skip unwatched movies** — `R3_CUTSCENE_SKIP_ALL` (default on; needs Hold to skip movies): the hold also skips movies you have not watched yet. The game's movie update (`func_003D6810`) only takes the skip button once the movie's seen bit is set (`func_003C84F0` at 0x003D6990); while the hold is pulsing, a hook (`tools/hooks/r3.json`) reports the bit as set, so the game ends the movie through its own skip path (Bink stopped, the movie marked seen, as after a normal skip). A plain Start press still behaves as on PS3, and the game's own waits (the first 1.5 s, the level still loading) stay. If 3 s of held pulses never register as a press, the same hook sets the game's skip flag (`PORT_SKIP_FORCE=0` turns that off). `logs\run.log` says how each movie ended (`movie closed: ended by ...`).
- **Subtitles** — not available: they are drawn by the game's Scaleform movies at a fixed size. Camera shake: no reduction option yet (no cheap hook into the camera-shake code has been found).
- **Discord Rich Presence** — `R3_DISCORD=1`, opt-in. Talks to the local Discord app over `\\.\pipe\discord-ipc-0..9` (no SDK): *Resistance 3* plus the current level (from the level folder the game opens; menus and lobby show *In the menus*). Needs an application id from discord.com/developers in `discord_appid.txt` in the game folder or `R3_DISCORD_APPID`. Silent when Discord isn't running (retries every minute).
- **Photo mode** — `R3_PHOTO` (default on): **F7** pauses the game and hides the port's overlays; **F12** takes the screenshot; F7 again resumes. No free camera (the camera is not hooked). HUD hide: `R3_PHOTO_HIDE_HUD` (default on; `0` = off) shows the last frame as it was right before the game drew its HUD (the frame-generation HUD split, which then also runs with frame generation off; needs DLSS/FSR/DLAA on; one extra copy of the display buffer per frame). If that frame had no cleanly separable HUD, the HUD stays and `logs\run.log` says `photo mode: no HUD-free image`.
- **Pause when the controller disconnects** — `R3_PAD_DISCONNECT_PAUSE` (default on): the game pauses with a message until the controller is back or Enter is pressed.
- **Benchmark** — launcher *Saves & tools › Run benchmark* (or `R3_BENCH=1`): a fixed input script from start-up into the campaign (`R3_BENCH_SCRIPT`, the `scratch\r3bench.ps1` route), measures `R3_BENCH_SECONDS` (default 60) and quits (`R3_BENCH_QUIT=0` keeps it running). Writes `logs\bench\R3_bench_<date>.txt` (average, 1 % and 0.1 % low fps, frame-time percentiles, draws per frame, µs per draw) and appends `logs\bench\bench_history.csv`. The button also sets `R2_BACKGROUND=run` for the run.
- **Benchmark capture key** — `R3_BENCH_KEY` (default `F11`; `F6`, `F5` or `off`; launcher *Interface › Overlays*, F9): press it in game to start recording frame times, press again to stop (also stops by itself after ~28 minutes at 240 fps). Each capture, like the scripted run, writes `logs\bench\R3_bench_<date>.txt` (mode, average fps, 1 % / 0.1 % low, stutter count, median / p99 / max frame time, frame cap) and `logs\bench\R3_bench_<date>.csv` (`frame,t_ms,frame_ms`, every frame), and appends `bench_history.csv`; the launcher's *Saves & tools* page shows the last result. **1 % / 0.1 % low** = the average fps over the slowest 1 % / 0.1 % of frames (CapFrameX style, not the percentile). **Stutter** = a frame more than twice the average of the previous 30 and at least 4 ms over it; a run of such frames counts once. F11 is free unless you bound it in `controls.txt`.
- **Save manager** — launcher **Saves & tools**: lists the saves (title, date, size), *Back up now*, per-backup *Restore* (current saves are backed up first) and *Delete*, and *Open* buttons. `R3_SAVE_BACKUP` (default on, newest 10 automatic backups kept): Play copies the save folder to `save_backups\<date>_auto` when it changed since the newest backup.
- **Per-save backups (automatic):** just before the game overwrites a save, the previous version of that save folder is copied to `saves_backup\<save folder>\<date>_<time>\` (UTC time; the newest backup always sorts last, even after a clock change) (next to `gamedata`; inside the save folder you chose when the saves live elsewhere), keeping the newest 5 per save. Unchanged saves and saves over 64 MB are not copied; a failure only logs one `[savebackup]` line and the game saves as normal. `PORT_SAVE_BACKUP=0` turns this off, `PORT_SAVE_BACKUP_KEEP=<n>` (1-100) keeps n. This is separate from the launcher's whole-folder backups in `save_backups\` (made when you press Play).  **To restore one:** close the game, open `saves_backup\<save folder>\`, pick the `<date>_<time>` folder you want and copy its files into `...\dev_hdd0\home\00000001\savedata\<save folder>\` (replace the files), then start the game.
- **Save location** — launcher Advanced › Saves *Save location*: **Game folder** (`gamedata\`, portable, the default), **Saved Games\Resistance 3** (`%USERPROFILE%\Saved Games`, survives deleting the game folder) or a folder you pick (*Saves & tools › Choose save folder*). It sets `PS3_GAMEDATA_ROOT`, which moves saves and the trophy record. On the next Play, when the new place has no saves yet, the launcher copies the game-folder saves (and `trophies\`) there; the old copy stays.
- **Import saves from RPCS3** — *Saves & tools › Import saves from RPCS3*: pick the RPCS3 folder (or its `dev_hdd0` or `savedata` folder). Every `savedata\<title id>...` folder of Resistance 3 (BCUS98176, BCES01118, BCJS37010, BCAS20215, BCKS10229) with a `PARAM.SFO` is listed for confirmation; your saves are backed up first (`save_backups\<date>_before-import`), then the folders are copied. A save of another region is renamed to this copy's title id (read from the game's `PARAM.SFO`, else from your saves) and its `SAVEDATA_DIRECTORY` entry is patched to match. A save in the same slot is replaced.
- **Mods list** — *Saves & tools › Mods* lists the folders in `mods\` in the order they are applied (a lower one wins a file two mods replace) with *Up* / *Down* / *Turn off* buttons. The order goes to `mods\order.txt` (one folder per line, `-Name` = off, `#` comments); mods it does not list come after, alphabetically; `_`/`-` folder names still disable a mod. Needs *Mods folder: On*.
- **Master volume / mono audio** — `PORT_VOLUME=<0..100>` (default 100) scales all game sound after the game's own mix; `PORT_AUDIO_MONO=1` (accessibility) mixes left and right together so nothing is lost on one ear or one speaker (the centre / LFE / surround channels are folded into the front pair by the downmix as before). Launcher Audio › Sound, F9, and the game's Options (*PC SETTINGS*); applies at once.
- **UI scale** — `PORT_UI_SCALE=<75..200>` (launcher Interface › Overlays *UI scale*, F9): size of the F3 overlay, the notifications and the port's menus. **Auto** (default) grows them with the window height (100 % up to 1080p, 125 % from 1440p, 150 % from 4K).
- **Frame-time graph** — the F3 overlay draws the last 120 frame times as bars under the numbers: green, yellow over 20 ms, red over 40 ms, with lines at 16.7 ms (60 fps) and 33.3 ms (30 fps). `PORT_OVERLAY_GRAPH=0` (launcher *Frame-time graph: Off*, F9) hides it.

**How to check them in game:** F9 opens *More PC Options*; the colour-blind filter changes colours at once; F7 = photo mode; unplug the controller during play = pause message; hold Space during a movie = skip; drag the window edge in windowed mode; Alt+Enter; `logs\run.log` lines start with `[r3x]`.

## Launcher settings

`Launcher.exe` has its own icon and artwork (original, drawn by `tools\art\make_r3_art.py`; nothing from the game). It writes your choices to `settings.ini` (its own) and `settings.bat` (`set "NAME=value"` lines that `run.bat` loads before starting the game), and the key bindings to `controls.txt`.

**Recommended for this PC / Auto-detect.** On first start the launcher detects your GPU (name, video memory, RTX or not, integrated or not), CPU cores/threads, RAM and screen (resolution and refresh rate), and shows a *Recommended* panel with a Low / Medium / High / Ultra tier and the settings it would use. **Auto-detect** applies them (display and graphics only). The same table is used by the game when `R2_PRESET=auto|low|medium|high|ultra` is set: it fills in every setting you did not set yourself. GPUs with DLSS get DLSS, others FSR 3.1 (or FSR 1 scaling on weak integrated GPUs). From a command prompt, `Launcher.exe --detect` prints what it found and the `settings.bat` it would write, and `Launcher.exe --table` prints the recommendation for a list of typical PCs (`--sim-gpu "<name>" --sim-vram <GB> --sim-cores <n> --sim-threads <n> --sim-ram <GB> --sim-screen <w>x<h>@<hz>` simulate other hardware).

**1080p rendered, DLSS output at 4K (supersampled on a 1080p screen):** Render resolution **3840 x 2160**, Anti-aliasing **NVIDIA DLSS**, Upscaling **Performance (50%)**, i.e. `RSX_RES_SCALE=3`, `RSX_FSR=2`, `RSX_UPSCALE=0.5`. The 3D scene is drawn at 1920x1080 and DLSS reconstructs 3840x2160, which is then scaled to your screen. This is the launcher's default. If DLSS isn't available (not an RTX card, or the DLSS runtime is missing) the port uses AMD FSR 3.1 instead, and if FSR 3.1 can't start either, FSR 1 spatial upscaling.

## Graphics options

- **Renderer:** the default is the *Compatible* renderer: the game's RSX (PS3 GPU) command stream is fed to RPCS3's RSX core and Vulkan renderer, built into the game as a library (`R2_RSX=rpcs3`). It uses RPCS3's settings from `rpcs3_config.yml` (next to the game, or `R2_RSX_CONFIG=<file>`), with the port's settings on top. *Native Vulkan* (`R2_RSX=vulkan`) is the port's own experimental renderer; it is hidden for now and only runs with `R3_RENDERER_FORCE_NATIVE=1`.
- **Direct3D 12 (not working yet - testing only)** (`R2_RSX=d3d12`, launcher *Renderer*): **Not working yet:** Direct3D 12 is an early work-in-progress renderer with many graphics bugs and much lower performance than Compatible; it is there for testing only, use Compatible to play. the port's own register-file draw engine (the one the native Vulkan renderer uses) driving a Direct3D 12 backend (`ps3recomp/libs/video/rsx_d3d12_engine.c` + `_pass.inc` / `_draw.inc`): guest vertex/fragment programs translated to HLSL and compiled with FXC (DXBC cached in `shadercache\d3d12\`), render targets / depth / textures / blits / readbacks / occlusion queries / per-viewport scissor, presented with a flip-model swap chain (`RSX_VSYNC`, tearing allowed with VSync off). Selectable on its own (not affected by the native-Vulkan hide). If no Direct3D 12 feature level 11_0 device is available, the game logs it and uses the Compatible renderer. Upscaler / anti-aliasing (`RSX_FSR`, launcher *Upscaler*): DLAA (`2`, NVIDIA DLSS through `r2_dlss.dll`), AMD FSR 3.1 native AA (`3`, `amd_fidelityfx_loader_dx12.dll`), Intel XeSS native AA (`4`, `libxess.dll`), all at full resolution, and FSR1 EASU + RCAS output scaling (`1`, `RSX_FILTER=fsr`, also the fallback when a provider can't start) -- unverified in game. HDR output (`R3_HDR` = `auto` / `1` HDR10 / `scrgb`, `R3_HDR_PAPER` / `_PEAK` / `_SAT`, as on Compatible; falls back to SDR when Windows HDR is off) and latency reduction (`R3_REFLEX` = 1 / 2 boost through NVAPI with latency markers, `PORT_LATENCY=antilag` / `auto` for AMD Anti-Lag 2 through the AMD Direct3D 12 driver extension) -- unverified. Point sizes / point sprites and wide lines are drawn through an expansion geometry shader (`RSX_D3D12_GS=0` turns it off), logic ops CLEAR / COPY / NOOP exactly and AND / OR / AND_REVERSE / AND_INVERTED as blends (`RSX_D3D12_LOGIC_OP=0`), R5G6B5 / A1R5G5B5 surfaces as native 16-bit targets (`RSX_D3D12_NATIVE_16BIT=0`) -- unverified in game; switching to the Compatible renderer (fallback) renumbers `RSX_FSR` to its values. Not available there yet: render-scale upscaling (`RSX_UPSCALE` < 1, `RSX_RES_SCALE`), frame generation and the Compatible-only graphics enhancements. Switches: `RSX_D3D12_DEBUG=1` (debug layer + DRED report on device removal), `RSX_D3D12_ADAPTER=<n>`, `RSX_D3D12_DUMP=<prefix>` (PPM frame dumps), `RSX_D3D12_FAIL_DUMP=<dir>` (HLSL FXC rejected), `RSX_D3D12_FLIP_FRONT=1`, `RSX_D3D12_DEPTH_RANGE=0`, `RSX_D3D12_DEPTH_LEGACY=1` (see `rsx_d3d12_engine.h`).
**Frame pacing, VSync and G-Sync / FreeSync** (Compatible renderer)

- Present mode per setting (the log prints it once: `[display] Vulkan present mode FIFO, 3840 x 2160`): VSync *Off* / `R2_PRESENT=immediate` = IMMEDIATE; *On* / `fifo` = FIFO; *Adaptive* = FIFO relaxed (MAILBOX if the driver has no FIFO relaxed); `R2_PRESENT=mailbox` = MAILBOX. *Auto* (`RSX_VSYNC=auto`) = FIFO whenever the frame rate is capped at or under the display refresh (the cap means it never waits on vblank) and Adaptive when uncapped or above the refresh.
- G-Sync / FreeSync follow FIFO, FIFO relaxed and IMMEDIATE. MAILBOX shows the newest frame at the fixed refresh, so VRR does not follow it: 60 fps on a 144 Hz screen then holds frames for 2, then 3 refreshes (judder) even with G-Sync on. Earlier builds mapped *Auto* and *Adaptive* to MAILBOX; they now use FIFO / FIFO relaxed.
- Without VRR, a fixed-refresh display is only even at a divisor of its rate (60 on 60 / 120 / 240 Hz, 72 or 48 on 144 Hz); the log warns (`[fps] note: ...`). **Refresh rate switch** — `PORT_REFRESH_SWITCH` (default off, `1` = on, experimental: every switch blanks the screen and can glitch audio; launcher *Display › Frame rate › Refresh rate switch*): in exclusive fullscreen (`RSX_DISPLAY=exclusive`) the display is switched to the nearest mode at the same resolution whose refresh is a multiple of the frame rate (`[fps] display switched 144->120 Hz`), and back to the desktop rate when the game loses focus, is minimised, leaves fullscreen, closes or crashes. Borderless and windowed never switch (use G-Sync / FreeSync or an even frame rate there) unless `PORT_REFRESH_SWITCH=2` (opt-in): any fullscreen, borderless too, switches the desktop rate the same way (144 -> 120 Hz for a 60 fps cap) and gives it back on focus loss / exit. With VRR the switch is harmless but unnecessary; `0` avoids the mode-change flash.
- **Display sync** — `R3_DISPLAY_SYNC` (launcher *Display › Frame rate › Display sync*; `PORT_DISPLAY_SYNC` when unset). `auto` (default): a background thread waits for the display's vblanks (D3DKMT) and checks over 2 s windows whether they follow the game's frames (VRR working) or keep a fixed period (`[display] VRR effective: yes` / `no -- the screen refreshes at a fixed 165.00 Hz`); it can only tell while the game shows fewer frames than the refresh rate, and windows while the game is minimized or another program is in front (plus the one after) don't count. After three "no" windows in a row (any other result in between starts over) fixed-refresh pacing turns on (`[display] fixed-refresh pacing ON`): present mode FIFO and the frame limit = refresh / k (/ the Frame Generation multiplier) for the smallest k within the frame-rate setting (60 allows up to 75), menus included, phase-locked to the vblanks when k ≥ 2, so every frame is shown for exactly k refreshes (`[display] fixed-refresh pacing: 165.00 Hz: 55.00 fps, each frame 3 refreshes`, `[fps] frame limit 55 fps (fixed-refresh pacing)`). Examples: 165 Hz 55 fps (Frame Generation 2x: 41.25 -> 82.5); 144 Hz 72 (FG: 72 -> 144); 120 Hz 60 (FG: 60 -> 120); 240 Hz 60 (FG: 60 -> 120); 60 Hz 60 (FG: 30 -> 60). With `R2_FPS=30` the frame-time floor is patched while it is on. Two "yes" windows in a row turn it off again. Not paced (frame limit and VSync as set) when even every refresh would mean under 30 rendered fps (60 Hz with Frame Generation 3x). `vrr`: never (only measured and logged); `fixed`: always; `off`: no measurement. The Reflex cap under the refresh rate is not used while it is on.
- Popup windows over the game (performance overlay, extra crosshair, toasts) make Windows compose the screen, which can turn G-Sync off while they are visible.

- **Occlusion kick** (on by default; `RSX_OCC_KICK=<draws>`, default `384`, `0` = off; `RSX_OCC_KICK_MIN_US=<us>`, default `750`): while the command buffer being recorded holds an occlusion query, it is submitted once it has that many draws and that much time has passed since the last submit, so the GPU starts the work in front of an occlusion report early instead of all at once when the report is flushed (the game polls these reports at `0x00274E64`; in the round 11 landscape claim->written was 9-15 ms). Only submit timing changes. `[occ] kick 5 s:` shows kicks/s and draws per kick. `RSX_GPU_TS=1` also prints `[gpu-ts] upscale 5 s:`, the GPU time of the DLSS / FSR evaluate with its AA passes.
- **Precise occlusion submit** (on by default; `RSX_OCC_PRECISE=0` = off, `RSX_OCC_PRECISE=<n>` (n > 1) = at most n per 16.7 ms, default 6; `RSX_OCC_PRECISE_MIN_US=<us>`, default `250`): the report addresses the game blocks on (the waiter at `0x00274E64`) are learned; when `GET_REPORT` claims a learned address again, the command buffer holding its query is submitted at once. Only submit timing changes; `RSX_OCC_KICK` stays the fallback. `[occ] precise 5 s:` shows learned addresses, submits and rate-limited claims.
- **Speculative-visible occlusion answers** (off by default; `RSX_OCC_SPEC_VISIBLE=1`, needs `R3_OCC_BLOCKING=1`; `RSX_OCC_SPEC_NEED=<n>`, default `2`): a late set whose reports were all visible in its last n real evaluations is answered visible at once instead of waiting (never hidden). A report-write fence on that report then keeps every set visible until the RSX wrote it and two more guest frames began (the late-write popping that made the blocking wait the default). `[occ] spec-visible 5 s:` shows avoided waits and the all-visible frames they cost. `RSX_GPU_TS=1`'s `[gpu-ts] 5 s:` line also shows the frame span, the GPU idle time between command buffers and the longest gap.

**Hitch logger** — `PORT_HITCH_LOG` (default on, `0` = off; `PORT_HITCH_MS=<ms>`, default 25): every game frame over 25 ms (or over 2x the frame-time target) prints one `[hitch]` line with where that frame went (game, limiter, sync waits, pad, RSX flip interval, present / acquire / GPU wait / DLSS, pipeline compiles, texture uploads, audio wait, and `present-iv` = the longest present-to-present interval). Every 5 s: `[hitch] 5 s:` (CPU frame time p50 / p99 / max) and `[hitch] present 5 s:` (present-to-present interval p50 / p99 / max, `uneven` = intervals more than 4 ms off the median, and how many frames a fixed-refresh display would hold for 1 / 2 / 3 / 4+ refreshes; a mix of 2 and 3 = judder unless VRR is active). Since this build the `[hitch]` line also splits `guestwait` (the game thread's own guest waits) into spin / sleep / lwmutex / lwcond and names the guest call site that waited longest (`top 0x... X ms`), shows the game thread's CPU time (`game X (cpu Y)`: a gap = the thread was preempted), and breaks down the RSX thread: `fifo-idle` (waiting for commands), `label ms/n` (NV406E semaphore waits), `zcull ms/n` (occlusion report reads waiting for the GPU), `hard-sync ms/n`, `submits n` and `rsx-limit` (RPCS3 flip limiter sleep). Hot-thread log lines (`[pipe]`, `[fps]`, `[hitch]`) are queued to a writer thread (`PORT_LOG_SYNC=1` writes them at once). Per-frame `[hitch]` lines are capped at `PORT_HITCH_LINES` per 5 s window (default 10, `0` = only the 5 s summaries; was 20 per second) and, with `PORT_HITCH_ADAPT` (default on, `0` = off), a frame is only listed when it is over max(`PORT_HITCH_MS`, 1.5x the frame-time target, 1.5x the previous window's p50), so a game running steadily below the target no longer logs every frame (frames over 2x the target still count in the summary).
- **RSX thread CPU split** (`PORT_RSX_CPU_PROF`, default on sampling 1 frame in 8 (whole flip-to-flip frames, scaled to per-frame averages; about 0.06 ms/frame instead of 0.42 ms when every frame is timed); `1` = every frame, `N` = 1 frame in N, `0` = off; also off with `PORT_HITCH_LOG=0`; `PORT_RSX_CPU_DETAIL=1` forces every frame). The `[hitch] 5 s:` line ends with `rsx-cpu per frame: work W = decode … state … shader … vertex … tex … surface … draw … zcull … submit … blit …; present … readback … label … idle …` (ms per frame).
  - `work` is the RSX thread's own CPU work: FIFO decode, draw state, program/pipeline lookup, vertex upload, texture cache, surface cache, draw recording, occlusion reports, submits and blits.
  - The time after `;` is flip/present, texture-cache readback waits, semaphore waits and FIFO-empty time.
  - Cost: one `rdtsc` per category switch.

**Frame pacing** — one pacer: when the frame rate is not 30, the game limiter (`R2_FPS`) paces the frame loop and the RPCS3 flip limiter is off (it was a second 60 Hz clock: the RSX thread slept in the flip while the game waited on it, then the next frame ran at once). `GCM_FRAME_LIMIT=vblank` restores the old double pacing.

**Game clock smoothing** — `PORT_DT_SMOOTH` (default on, `0` = off): above 30 fps the game clock steps by the mean of the last 8 frame times instead of each raw frame time, so an uneven pair of frames (e.g. 1 ms + 32 ms) on an even display no longer makes objects jerk; the total game time is unchanged.
- **Frame rate:** 60 fps by default (the game was 30 fps on PS3). The game's own frame limiter is replaced by a precise PC-side one (high-resolution timer plus a short spin), the same idea as RPCS3's "Unlock FPS" patch, and RPCS3's vblank follows the chosen rate. The game clock's 1/75 s minimum step is lowered too, so 120/144 fps and Uncapped run at the right speed; cutscenes that use a fixed step per frame are kept at real-time speed. 30 fps uses the game's original limiter. *Just under refresh* (`R2_FPS=vrr`) caps a little below the display's refresh rate (e.g. 138 fps at 144 Hz) so a G-Sync / FreeSync display stays in its variable-refresh range. `R2_PACE=0` uses the older, less precise wait; `R2_PACE_SPIN_US=<µs>` (default 500) sets how long the limiter spins before a frame.
- **Display mode:** borderless fullscreen, exclusive fullscreen or windowed, with VSync off / on / adaptive / auto.
- **Anti-aliasing → NVIDIA DLSS** uses DLSS on GeForce RTX cards and falls back to FSR 3.1, then FSR 1, on other GPUs. The DLSS SDK is downloaded by Setup into `tools\dlss` (if that fails, the port still builds without it). `RSX_DLSS_PRESET=<letter>` forces a DLSS model preset.
- **Upscaling** (with FSR or DLSS on): Native (DLAA), Quality, Balanced or Performance. Menus and HUD stay at full resolution.
- **Intel XeSS (experimental, Compatible renderer):** XeSS 2 (`rpcs3/Emu/RSX/VK/VKR2XeSS.cpp`, Vulkan `xessVK*` API, Intel's `libxess.dll`; runs on any GPU through DP4a) is hooked into the RPCS3 renderer's upscaler. Pick **Intel XeSS** in the launcher's upscaling option, or set `RSX_FSR=4`. If XeSS can't start, or on the native renderer, FSR 3.1 is used instead. The preset follows the Upscaling ratio (Native → Native AA, Quality → Ultra Quality, Balanced → Quality / Balanced, Performance → Balanced / Performance). `RSX_XESS_QUALITY=aa|uqp|uq|q|b|p|up` asks for a preset, `RSX_XESS_JITTER_SIGN=-1` / `RSX_XESS_JITTER_SIGN_Y=-1` flip the jitter, and `RSX_XESS_LOG=1` logs XeSS's own messages. Setup downloads the XeSS SDK (`tools/xess/`) after you accept Intel's licence.
- Resistance 3 renders each frame across the console's buffer flip (a geometry pre-pass, then lighting and a material pass). The upscaler follows that, so DLSS / FSR run on the finished image, not the G-buffer. The upscaler locks onto the scene size once it is stable, so it isn't reset by menus or small passes, and briefly backs off instead of resetting when it can't find the scene for a frame or two.
- **CPU profile** (Performance page): Auto picks from the cores the game can use (logged as `[cpu]`). Low (≤4 cores) turns off the timing spin-waits, folds the Vulkan submit thread into the render thread and uses fewer shader-compiler threads; below 8 CPU threads it also runs the RSX thread (`rsx::thread`) above normal priority, so the other game threads stop taking its core (`PORT_RSX_PRIO=0` turns this off, `1` forces it with any profile but Off; log: `[cpu] rsx::thread (thread N): priority above normal`). Mid (6 cores) shortens the spin-waits. High changes nothing. The port also spreads its main, RSX and FIFO threads over separate cores, keeps them on P-cores on hybrid Intel CPUs and lowers background threads. Advanced: `PORT_CPU_PROFILE=auto|low|mid|high|off` (settings you set yourself always win); `PORT_THREAD_PLACEMENT=0` turns off thread placement; `PS3_PRIO_BOOST=0/1` forces priority boosts off or on; `PORT_MAIN_CPU=<n>` pins the main thread to CPU n.
- **Low-end PCs:** use **Auto-detect**. On CPUs with fewer than 8 threads the port stops raising thread priorities (except the RSX thread's, `PORT_RSX_PRIO`) and pinning threads to cores, and its busy-wait loops give the CPU to other threads. If a 4-core PC still stutters, use 30 fps.

### Graphics enhancements (Compatible renderer, all off by default)

- **Shadow resolution** (`RSX_SHADOW_SCALE=2|4`): the game's shadow maps (square, depth-only render targets from 256 to 2048 pixels) are rendered at 2x or 4x resolution and sampled at that resolution; the slope-scaled depth bias is scaled to match so no new shadow acne appears. The log says `[r2gx] shadow map target ...` for each one found. Costs GPU time and video memory (4x on a 2048 map is an 8192 map).
- **Shadow map scale cap** (`RSX_SHADOW_SCALE_CAP=<percent>`, default off): renders the game's shadow maps (every Z16 depth-only target up to 2048 of any size or aspect, so maps packed side by side share one scale, plus square power-of-two depth-only targets of 256-2048) at most at this resolution scale instead of the global one (at 300% a 1024² map is 3072²). `200` or `100` saves GPU time on the shadow passes; shadows get softer than at 300% (100 = the PS3's own sharpness). The scaled slope depth bias follows the cap. Ignored with `RSX_SHADOW_SCALE=2|4`. Logged as `[r2gx] shadow map ... capped to N%`.
- **Native shadow maps** (`RSX_SHADOW_NATIVE=0|1`, default 1 (on)): renders Z16 depth-only shadow targets (any size up to 2048, including the 256x64 strips packed next to the square maps) at the PS3's native 100% scale, with no scaled slope bias. This is the R3 carpet/basement-floor fix: at 300% the tightly packed Z16 shadow maps (sampled as combined taller textures whose layout changes with the camera) were read through scaled atlas gathers with the game's bias tuned for PS3 texels, giving hard straight-edged dark regions. Shadows are PS3-sharp; set `0` for scaled shadow maps. Takes precedence over `RSX_SHADOW_SCALE`/`RSX_SHADOW_SCALE_CAP`, which only apply to maps it does not cover (set `RSX_SHADOW_NATIVE=0` to use them on Z16 maps). Logged as `[r2gx] shadow map WxH ... native 100%`. All three detect depth-only passes by checking only the active colour slots (R3 leaves stale addresses in inactive MRT slots).
- **Shadow slope bias multiplier** (`RSX_SHADOW_SLOPE_K=<k>`, default 1 (off), 1-8): multiplies the polygon-offset slope factor of the shadow maps (every Z16 depth-only target up to 2048, plus `RSX_SHADOW_SCALE`'s square maps), on top of any resolution ratio from the native / cap / `RSX_SHADOW_SCALE` paths; maps none of them rescales keep their resolution and get only the extra slope (R2 defaults, scale <= 100% or <= the cap). More caster bias against self-shadow acne (hatched stripes on grass blades and other thin or grazing casters); too much detaches contact shadows. Try `2`. Logged as `[r2gx] shadow slope bias xK ... shadow-map binds` every 5 s.
- **Precise vertex-program dot products** (`RSX_VP_PRECISE_DOT`, default 1 (round 11 briefly defaulted it to 0 as a rubble-garbage suspect; the garbage persisted, so it is back on); `0` = plain fp32 `dot()`): the DP4/DPH of every translated vertex program (and the vertex interpreter) use a compensated Dot2 sum. The scene sits in the last few percent of standard-Z depth, so plain fp32 rounding of world position x view-projection gave each mesh a few D24 steps of camera-dependent depth noise and the cut line between a poster and the wall behind it crawled by several pixels from frame to frame (poster edge flicker). Identical in pre-pass and EQUAL passes, so material passes still match.
- **Unjittered effect draws** (`RSX_FX_UNJITTER`, default 1 = additive effects; `2` = every blended effect draw; `0` = off): effect draws into the scene before the upscaler that write no depth and do not test EQUAL skip the camera jitter. Dust motes are ~1 render-pixel additive quads; jittered, the jitter phase decided whether they covered a pixel centre, and the DLSS bias mask shows that raw (sparkles popping in and out). Logged as `fx unjitter`.
- **Light quad jitter** (`RSX_AA_LIGHT_JITTER=0|1`, default 1 (on) since round 10): the deferred light quad (stencil-tested, 3-6 vertices) gets the jitter shift of its stencil marks, so the view ray it interpolates pairs with the jittered depth of the same sample. Off, the rebuilt position is off-surface by dz/dx x jitter, which moves shadow edges on grazing floors and toggles self-shadowing on thin blades every frame (white-noise flicker DLSS cannot converge). Logged once as `light quad jitter f...` and counted in the 5 s `light quads given their stencil marks' jitter` line.
- **Scaled depth copies are one GPU blit** (`RSX_DEPTH_BLIT_DIRECT`, default `1`, `0` = the upstream carrier path): when the game copies a depth buffer to a depth buffer of another size (Resistance 2 fights: about 20-30 per frame at 300%; the same RPCS3 path is used here), RPCS3 on Turing+ NVIDIA sent each copy through a colour carrier: depth and stencil separately, image -> buffer -> colour image -> scaled blit -> buffer -> image, with a barrier between every step. In Resistance 2 a RenderDoc replay of a fight frame put those buffer copies at 30.6 ms of the frame's 40 ms GPU time; all draws together were about 4 ms. Now the depth buffer is blitted directly with nearest filtering when the GPU supports blits of that depth format (logged once as `[rsx] depth scale blits for format ...`), which selects exactly the same texels, so the result is bit-identical. Falls back to the old path when the format has no blit support, when the copy is linear-filtered (`RSX_BLIT_EXACT=0`) or the image is copied to itself.
- **No inherit copy before the upscaled-scene writeback** (`RSX_WB_SKIP_INHERIT`, default `1`, `0` = old): under DLSS/FSR/XeSS the upscaled image is copied into the full-resolution scene surface. RPCS3 first filled that surface with a scaled copy of the reduced-scale scene (and could clear or reload it from memory) that the copy then overwrote completely: a 2560x1408 -> 3840x2112 blit every frame at 300% (Resistance 2 RenderDoc 2684 EID 2715; the same writeback code is used here). When the copy covers the whole surface that step is skipped.
- **4-sample effect targets at their sample resolution** (`RSX_AA_SAMPLE_RES`, default `1`, `0` = old): DLSS/FSR/XeSS turn host MSAA off, so a PS3 4x (2x2) antialiased target became a 1-sample image at its pixel size, although its memory holds the 2x2 sample grid. Resistance 2's half-size effect buffer (640x352, 4x) shares its memory with the 1280x704 post buffer that way: every switch between the two copied the post image down to half size and back up with nearest filtering, about 15 times a frame (RenderDoc 2684 EIDs 2785/2830), so the post chain and the final picture were a pixel-doubled half-resolution copy of the upscaled image (and the depth buffer made the same trips). These targets are now drawn at twice the scale (one pixel per PS3 sample), so the copies are exact 1:1. Only targets whose sample grid fits within the scene size are affected.
- **Blit trace** (`RSX_BLIT_TRACE=N`, default off; `1` = 300 lines): prints `[blit]` lines for the first N game blits (NV3089: guest source/destination address, pitch, size, scale, host rectangles, filter) and surface-cache inheritance copies (address, pitch, native size, samples per pixel, scale, rectangles). For diagnosing blurry or pixelated passes.
- **Effects resolution** (`RSX_FX_FULLRES=1|2`): render targets at half (`1`) or also quarter (`2`) the scene size (particles, smoke, glow / bloom, blur and depth-of-field buffers) are drawn at the scene's resolution; the game's own upsample and composite passes read them through the renderer's scaling, so they stay aligned.
- **Ambient occlusion** (`RSX_SSAO=1`, experimental): a screen-space AO pass computed from the scene depth when the scene pass ends, before the game's post-processing. Not available with `R2_MSAA`. With DLSS, FSR or XeSS it runs on the upscaler's input (internal resolution, same frame and jitter as the scene the upscaler gets), just before the upscale; `RSX_SSAO_DLSS=0` turns it off under DLSS only, `RSX_SSAO_UPSCALER=0` restores the old post-upscale trigger (diagnostics only). `RSX_SSAO_STRENGTH=0..1` (0.6), `RSX_SSAO_RADIUS=0.1..8` (1.0); `RSX_SSAO_DEBUG=1` shows only the AO term.
- **Texture packs** (`RSX_TEXDUMP=1`, `RSX_TEXPACK=1`): dump writes each texture once to `texdump\` as `<key>_<w>x<h>_<format>_m<mips>.dds` (DXT1/3/5, with mips) or `.png` (A8R8G8B8), listed in `texdump\manifest.tsv`; the key is a content hash of all mip levels plus size, format and mip count (stable across runs, not a memory address); copy edited files into `mods\textures\` (sub-folders allowed; the leading 16-digit hash is what matters) and turn on the pack. Replacements keep the DXT format for `.dds` and either the original size or 2x..8x it with every mip level (HD, see below). A `<folder>` value uses another folder. With both off the upload path costs one `bool` test.
- **HD UI pack** (`RSX_HD_UI=1`; experimental, off until you make a pack): AI-upscaled menu / HUD / loading-screen textures, made on your PC from your own game (nothing game-derived ships with the port), like the Bloodborne PC port's 4K UI mods. Most of the HUD is Scaleform vector art and text, which already renders at full resolution; this sharpens the bitmap parts (icons, button prompts, map and menu art). **One click:** launcher › Saves & tools › **Create HD UI pack**. It runs `HDUIPack.exe` (built with the port, nothing to install): it reads the menu / HUD textures straight from the game's archives (`USRDIR\packed\**\*.psarc`, the images the Scaleform menus show), upscales every texture with Real-ESRGAN on the graphics card (`tools\hdui_upscaler\`, comes with the port: Real-ESRGAN-ncnn-vulkan built against ncnn 20261020, SHA-256 checked before every run, with the official `realesrgan-x4plus` model, taken from Real-ESRGAN's release zip, downloaded once (45 MB, SHA-256 pinned); alpha separately, so edges stay clean; textures under 64 px are padded with their edge pixels for the model and cropped back) to 2x..4x the original (4096 px per side at most) and writes DDS files in the game's own format with every mip level to `mods\hd_ui\`. The launcher shows progress (done / total, time left) and can cancel; when it finishes it turns HD UI pack on and shows a summary. A full pack (~1300 textures) takes a few minutes on a recent graphics card (about 1.5 hours on a 6-core CPU if it falls back to the CPU) and a few GB of disk; running it again continues where it stopped (finished textures are kept, also after a cancel) and **Update HD UI pack** only makes what is missing. Every upscaled texture is compared with the original (reduced back to its size); one that does not match (damaged output) is not used: from the graphics card it is made again on the CPU, and if the CPU's is unlike it too the game keeps the original texture and `pack.tsv` notes it as `refused` so later runs leave it alone (`HDUIPack.exe --force` tries again). Textures an earlier version made with another model before this check are made again by the next Update. **Remove HD UI pack** deletes `mods\hd_ui\` and turns the option off (the launcher waits for the deletion to finish; anything an ended removal left in `mods\.hd_ui.removed` is deleted by the next run). Without a usable graphics card it runs on the CPU (see *GPU safety*). How it matches the game: the key the game's texture upload computes (a 64-bit hash of the texel data, size, format and mip count) is computed by the tool from the same archive bytes with the same code (`rpcs3/Emu/RSX/Common/r2_hd_ui.h`), so no dumping or playing is needed. The pack is built beside it in `mods\.hd_ui.stage` (a dot folder, which nothing loads; on the same drive, so `--out` and `--tools` may be on different drives) and renamed into place, so an interrupted run never leaves scratch files where the game loads replacements; if a run is cancelled between the two renames, the next run puts the new (or else the previous) pack back, and while a file is held open (antivirus, Explorer) it keeps both and says so instead of deleting anything. In game the log says `HD UI pack: N texture(s) in mods\hd_ui` at start and `HD UI pack: N texture upload(s) replaced so far` as they are used. A replacement is 2x..8x the game texture (same factor on both axes, 8192 px per side at most) and is drawn over exactly the same screen area, so layouts do not change; files that do not match (size, format, missing mips) are skipped with a log line and the game's texture is used. Copies (blits) from a replaced texture are taken from the game's own texture, so they are never cut off. `RSX_HD_UI=<folder>` uses another folder; `RSX_HD_UI_CACHE_MB` (default 512) caps the decoded replacements kept in memory. **GPU safety:** the AI upscaler runs on the graphics card (Vulkan) in **one** upscaler run for all textures, with the upscaler's own tile size and job counts, the way the Bloodborne PC port (Lantern Engine) runs the same Real-ESRGAN with the same model, which works on an RTX 5070 (earlier versions started the upscaler hundreds of times with tiny tiles and the remacri model; on an RTX 5070 that ended in NVIDIA driver resets, nvlddmkm 13 / 153, and a PC restart). If anything goes wrong on the graphics card (the upscaler's own stop at the first failed GPU submission, `GPU_STOP`; a lost device, `vkQueueSubmit failed -4`, seen by the watchdog; 90 s without progress; a crash or no output) the upscaler is ended at once, so nothing more is sent to the graphics card; the textures it already made are kept and the rest are made on the CPU (`tools\hdui_upscaler\bin\realesrgan-ncnn-cpu.exe`, which contains no Vulkan code at all, with the bundled `fast` model, at below-normal priority on about half the CPU threads). The failure is recorded in `tools\upscaler\gpu_fault.txt` and later runs use the CPU until you delete that file (e.g. after a driver update) or run `HDUIPack.exe --use-gpu` (when that run makes everything on the graphics card, the file is removed). When no usable Vulkan graphics card is found or the GPU upscaler does not start (no fault), that is recorded in `tools\upscaler\gpu_unavailable.txt`: later runs keep the textures the CPU made with `fast` instead of making the whole pack again, and each **Update** first runs one small test image on the graphics card; once it works (e.g. after a driver install) the file is removed and those textures are made again with `x4plus`. `tools\upscaler\upscaler_running.txt` exists only while the GPU upscaler runs; if it is still there after a reboot and Windows logged an unexpected shutdown at its next start (Kernel-Power 41 / EventLog 6008 within minutes of the first start after the run), or Windows' log cannot tell, that counts as a failure too and the marker and the upscaler's log are kept as `tools\upscaler\upscaler_crashed.txt` / `.log`; a normal restart or sign-out does not count. `HDUIPack.exe --cpu` uses only the CPU; `--safe` runs the GPU in conservative mode (`-c`: fp32 storage, no fp16 / int8 / cooperative-matrix / subgroup ops) with `-t 64` tiles and `-j 1:1:1`; `--status` prints where the next run upscales (`@gpu gpu|cpu ...`) and starts nothing. Advanced: `HDUIPack.exe --help` (`--model x4plus` (the default on the graphics card) / `fast` (the default on the CPU) / `remacri` / `ultrasharp` (sharper ESRGAN models for personal use), the larger ones downloaded once into `tools\upscaler\models\` and SHA-256 checked and about 30x slower than `fast` on the CPU; `--use-gpu`, `--cpu`, `--force`, `--safe`, `--status`, `--dry-run`, `--list`, `--gpu N`); the older dump-based path still works for textures outside the archives: set Dump textures to **Menus / HUD only** (`RSX_TEXDUMP=ui`), play, then `python tools\hd_ui_pack.py` (Python 3 with Pillow and numpy) writes to the same folder. Tests (offline, no game run): `cmake -S project\tests\hd_ui -B build\hd_ui_test -G Ninja -DCMAKE_CXX_COMPILER=clang-cl -DCMAKE_C_COMPILER=clang-cl` then `cmake --build build\hd_ui_test` and `ctest --test-dir build\hd_ui_test` (`hdui_upscaler_install` checks the pinned upscaler files and runs a test image through the real CPU-only build; `hdui_gpu_safety` checks the command line, the GPU-or-CPU choice after a fault, that a crash's evidence is kept, the watchdog on a stand-in upscaler, the padding of small textures and the single GPU run handing the rest to the CPU after a lost device, without starting the Vulkan upscaler; with the game files present, `hdui_real_keys` checks every key against RPCS3's own upload layout code). The `x4plus` and bundled `fast` models are BSD-3-Clause; the optional remacri / UltraSharp models are for personal use (CC BY-NC-SA); do not share the generated pack.
- Not done for Resistance 3: higher-quality motion blur / depth of field beyond what *Effects resolution* gives (they can be turned off: *Post-effect toggles* above). The shadow-safe FOV, ultrawide and LOD distance options (below) are implemented but not yet tested in game.
- **FOV, ultrawide and LOD (camera hooks, not yet tested in game):** the field-of-view setting is applied in the game's camera frustum setter (`func_00799EF0`), so the shadow cascades, light tiles and culling get the widened frustum (2026-11-14 audit: the LOD setters are compensated and the native SPU kernels (Edge zlib, Bink IDCT, DOF) do no culling; no path that rebuilds a culling frustum from the original FOV was found, though about 30 other `tan()` callers and the lifted SPU visibility-job inputs were not traced individually). The old constant patch at `0x00F0608C` only changed the projection, which is what caused black bands at the screen edges (RPCS3 issue #14124). Switches: `R3_FOV_SAFE=0` goes back to the old constant patch; `R3_FOV_VIEWMODEL=1` also widens the first-person weapon (off by default, so the arms are not distorted); `R3_LOD_SCALE=1.5` / `2` / `3` (launcher *Level of detail distance*) multiplies the LOD distance in the LOD setter (`func_0079C918`) and in its no-store twin (`func_0079C810`, used by the object draw-distance tests); `R3_LOD_FOV_COMP=0` turns off the automatic LOD correction for the wider FOV (by default a wider FOV does not make models switch to lower detail sooner).
- **No GPU load shedding (`R3_NO_LOADSHED`, default on; launcher *Load shedding*):** the game's per-frame governor (`func_003DCA40`) compares the previous frame's RSX time with its PS3 budget and, on "slow" frames, multiplies the LOD distances by 0.75 and drops the scene from 960x704 to 960x640. On PC those times are host times, so heavy view directions tripped it frame by frame: models and textures popped in and out with the view angle, and the DLSS/FSR input changed size. The port makes the budget constant (`0x003DCA20`, 2000.0) huge, so every frame takes the game's full-detail path. `R3_NO_LOADSHED=0` restores the PS3 behaviour.

### Renderer switches (advanced, `settings.bat`)

All optional; unset = the default shown. Each is logged at start-up in the `[r2rsx] perf:` line.

| Variable | Effect |
|---|---|
| `R2_RSX_PROF=1` | Every 5 s, prints a block of `[r2rsx-prof]` lines to the log: CPU time of each RSX thread, the renderer's frame phases, draw and framebuffer-bind time, command-queue flushes (by caller), ZCULL report waits, memory faults that needed a GPU readback, and vertex uploads. It also prints the RSX thread's busy time without DLSS, the time spent outside draws (flushes, flips, ZCULL, blits, labels), deferred ZCULL labels, and program-cache hits (`MRU hits`, `pipeline memo hits`, `re-sent FP kept`, `re-sent VP kept`; `program slow-path loads` counts the full cache lookups that remain). For finding what limits the frame rate. |
| `R2_SHADER_THREADS=<n>` | Background shader-compiler threads (default: what the CPU profile leaves free). |
| `R2_SHADER_CACHE=0` | Don't keep compiled shaders on disk (`shadercache\rpcs3`). |

| `R2_WCB=0/1` | Write colour buffers back to memory (needed for some effects; default: the config file's value). |

By default (`1`) these are byte-identical but copy 32-byte runs, only touch the source rows and columns the blit reads, and reuse a per-thread buffer: a 1280×720 32-bit blit source went from 5.4 ms to 0.46 ms, its re-tile from 4.2 ms to 0.7 ms (micro-benchmark). The CPU blit source window now also covers vertically flipped blits (which read upwards from the source), horizontally flipped blits (which read right to left), clip rectangles taller than the source, and the unpadded read of swizzled blits to sizes that are not a power of 2. The first three used to read past the scratch buffer, and the last one read stale bytes between rows (`RSX_BLIT_DETILE_SRC=0`, old name `R3_BLIT_DETILE_SRC`, turns the source detile off). | `RSX_FLARE_SMOKE_OCCLUDE=1/2`, `RSX_FLARE_SMOKE_STRENGTH=<1..4>` | **Experimental, not yet tested in game, off by default.** Lens flares and machine lights shining through smoke (probably also how the PS3 looks: the flares are additive with the depth test off, and smoke only dims them by `1 - alpha`). Flares are drawn into a side image; every smoke draw after them dims that image `STRENGTH` times (default 2) instead of once, then it is added onto the scene. `1` = flares only, `2` = also depth-tested glows and sparks. Smoke drawn *before* a flare doesn't dim it more. `STRENGTH=1` must look identical to off. `[r3fx]` stats line every 600 frames. |
| `R2_FBB_KEEP_WCB=1` | Restores RPCS3's original behaviour of writing a render target back when it is re-bound as the same surface (the port skips that redundant copy). |
| `R2_ZCULL=sync` / `relaxed` / `off` | Occlusion queries. *relaxed* (the default, and RPCS3's recommended setting for Resistance 3) reads only finished results and never makes the renderer wait for the GPU, so visibility can lag one frame. *sync* is strict: every report waits for the GPU (the first bench spent ~8.5 ms per frame on that). *off* reports everything visible. In strict mode, report reads are batched, the wait sleeps on the GPU fence instead of polling, and pending memory-fault flushes are serviced while waiting. |
| `R2_ZCULL_DEFER=0` | In strict mode, label writes that would wait for pending ZCULL reports are deferred and written once the reports finish (default on; `0` restores the immediate wait). |
| `R2_ZCULL_FLIP_LAG=<n>` | **Experimental, may hang (default 0 = off).** In strict ZCULL mode, deferred labels still waiting on the GPU at a flip are carried over up to `n` flips instead of being waited for at every flip; they are also released whenever the RSX command queue runs dry. With `1` the game hung ~30 s into Haven in one bench, so leave it off. |
| `RSX_ZCULL_FLIP_CLEAR=1` | Default: occlusion queries still running at a flip are kept (RPCS3 issue #18148 A/B); `1` restores RPCS3's discard. Old names `R3_ZCULL_FLIP_CLEAR` / `R2_ZCULL_FLIP_CLEAR` still work. Logged as `[zcull] flip keep (default; RSX_ZCULL_FLIP_CLEAR=1 reverts)`. |
| `RSX_ZCULL_COUNT=approx` / `precise` | Occlusion-query counts. *approx* (default; RPCS3's "ZCULL Accuracy: Approximate", the recommended Resistance 3 setting) reports any visible pixel as fully visible. The game hides an object when its occlusion box's pixel count is at or below a per-object threshold. Here that box is drawn at the reduced DLSS/FSR scale with a moving sub-pixel jitter, so near the threshold the exact count changed from frame to frame and with the camera angle, and objects such as Haven's carpet clipped in and out. *precise* restores the exact counts. The upscaler then flipped between the two pairs, with history resets, re-creations and 1-2-frame flashes of magenta/green rock facets (the G-buffer normals). `0` restores the old vote. |
| `RSX_AA_CLASSIFY_HOLD=N` | DLSS/FSR scene detection. Default `4`. Previously the depth-copy pair `c19c0000/c1380000` won those windows (Death Squad / firing purple-green tints, DLSS resets). `0` turns this off. |

Classifies where every bound fragment texture comes from (`upload`, `rt`, `rt-copy`, `blit`, `deferred`) and logs `[texsrc]` lines for new texture addresses whose source surface does not match (`FMT`, `BPP`, `DEPTH`, `SWZ`, `SIZE`) or whose memory upload overlaps a live GPU surface (`OVER`, i.e. possibly stale guest memory); `2` logs every new address. A summary line every 2 s. `RSX_DEBUG_TEX_SRC_LINES=<n>` caps the lines (3000). |
| `RSX_DEBUG_TINT_SURFACE=<mask>` | Diagnostics: draws whose textures match the mask sample solid green instead. `1` format / texel-size mismatch (`FMT`, `BPP`; `SWZ` and `SIZE` are log-only, `SIZE` matches every post pass reading a resolution-scaled target), `2` depth read as colour (also full-screen post passes), `4` any surface (render target) source, `8` memory upload over a live surface (`OVER`, re-tested on every draw), `16` `OVER` on textures of at most 64x64 (the rubble chunks' 16x16 textures); add them. Depth-format textures are replaced by a depth image cleared to 1.0 instead, so they show a flat colour that is not necessarily green; multisampled textures are never replaced. `RSX_DEBUG_TINT_ADDR=<hex>[,<hex>…]` also tints the listed texture addresses (from the `[texsrc]` log) whatever their source, for bisecting which texture is the garbage. |
| `RSX_RDOC_FRAMES=<n>` | RenderDoc (`renderdoc.bat`): `F6` captures `n` whole guest frames, starting and ending at the game's flips (F12 captures one host present, which is only half a guest frame). `RSX_RDOC_KEY=F<n>` or a hex virtual-key code changes the key; `RSX_RDOC_AT=<flip>` captures automatically at that guest flip. Logs `[rdoc]`. |
| `RSX_FLUSH_KEEP_NEWER=0` | Fix (default on; shared with R2). Writing a render target back to guest memory skips the rows of newer surfaces that overlap it, so a dead older target cannot overwrite them. Fixes purple / rainbow / checker bullet-rubble chunks: the game renders the chunk textures into 16x16 targets packed 0x80 bytes apart, and an older target's write-back trampled the newer ones, which were then re-read from the trampled memory. Also skips a write-back only when it is wholly excluded (upstream skipped it as soon as one exclusion lay inside it). `0` = upstream. |
| `RSX_AV_NEIGHBOUR_SMALL_FLUSH=0` | Fix (default on; shared with R2). A CPU/SPU access fault next to a render target of at most 64x64 (`RSX_AV_NEIGHBOUR_SKIP`) writes that target back instead of releasing it dirty. The game packs the 16x16 rubble targets into a ring it also fills with CPU data; the skip lost their GPU data, and the chunk textures read stale index/vertex bytes (purple / rainbow / checker chunks, round 14). Costs a GPU sync per such fault while shooting; larger surfaces are still skipped. Counted as "small ones written back" in the `[rb-attr]` report. `0` = skip them too. |
| `RSX_NV0039_PREINVAL=0` | Fix (default on since round 16; shared with R2). Before an NV0039 buffer copy, the protected texture-cache pages of its destination are invalidated in one pass on the RSX thread, instead of one access fault per page during the copy (`[hitch] rsx nv0039` showed 0 faults and ~1.5–2 ms of pre-invalidation per long flip, no stale or black textures). `0` = the old fault-per-page behaviour. |
| `RSX_DEBUG_SMALL_RT=1` | Diagnostics (shared with R2): `[smallrt]` lines for render targets of at most 64x64: `FB` (framebuffer setup with clip/scissor/viewport), `BIND` (size, format, scale, overlapped surfaces newer/older/dirty/tag-miss), `DROP` (a surface discarded because its memory was overwritten), `KEEP` (a write-back that skipped newer surfaces), `NFLUSH` / `NSKIP` (a neighbour fault that wrote a small target back / released it dirty with `RSX_AV_NEIGHBOUR_SMALL_FLUSH=0`). `RSX_DEBUG_SMALL_RT_LINES=<n>` caps the `FB`/`BIND` lines (4000, at most 60/s); `RSX_DEBUG_SMALL_RT_EVENT_LINES=<n>` caps the others separately (4000, at most 120/s). |

## Shader precompile and rebuilding the shader cache

Shader caches are never shipped with the port: they are built on your PC, from the shaders your game uses, the first time each one is seen. Launcher, Performance page, **SHADER CACHE**:

- **Compile shaders before playing** (default On, `PORT_SHADER_PRELOAD=1`, which means `R2_PRELOAD_BOOT=-1`; an explicit `R2_PRELOAD_BOOT` still wins): at start-up the Compatible renderer builds every pipeline in its disk cache before the game gets its first frame (the game's RSX context waits for it), so nothing seen before compiles during play. Progress: a centred **Compiling shaders N / M** panel with a progress bar, drawn into the game image (`R2_PRELOAD_OSD=0` uses a separate window, not shown over exclusive fullscreen) and log lines `[r2rsx] shader preload: compiling every cached pipeline before the game starts on N threads`, `compiling n/N pipelines`, then `done, every cached pipeline is ready`. A few seconds with a warm driver cache, a minute or two after a driver update or a rebuild. Off (`PORT_SHADER_PRELOAD=0`): nothing is built at start-up, in the background or replayed from the Fossilize database; each pipeline is built when the game first draws with it (can hitch briefly; log `[r2rsx] shader preload: off`). Pipeline creation is SEH-guarded everywhere (boot and background preload, Fossilize replay, render and compiler threads; `PORT_PRELOAD_SEH=0` disables): a driver fault skips that pipeline and its draw, stops the preload and replay, and the preload pipeline is quarantined. On AMD GPUs pipelines are created one at a time (`PORT_PIPE_SERIAL`, default 1 on AMD, 0 elsewhere). The launcher's **Compile shaders before playing** sets `PORT_SHADER_PRELOAD` (the same switch in all three Resistance ports, default on; `off`/`0`/`false`/`no` turns it off). Every start logs `[shaders] loaded N cached pipelines in X ms (...)` once the cached pipelines are built (with the option off, `0 ... (preload off, on demand)`). `PORT_SHADER_PRELOAD_BUDGET=<seconds>` (old name `R2_PRELOAD_BOOT_BUDGET`, used when the new one is unset or not a number; default 0 = no limit, negative counts as 0) stops the preload after that long, as if skipped.
- **Shader compile threads** (`R2_PRELOAD_BOOT_THREADS`, default Auto = every logical core but one, 1 to 64): the threads that build the pipelines before the game starts.
- **Rebuild shader cache** (button, asks first; refused while `Resistance3.exe` is running) deletes the compiled, driver-specific part and keeps the list of shaders and pipelines to build, so the next start with Compile shaders before playing on rebuilds all of them. Deleted, from `shadercache\` and from its backup in `%LOCALAPPDATA%\Resistance3Port\shadercache` (`run.bat` restores missing files from there):
  - `rpcs3\shaders_cache\vk_pipeline_cache.bin` (and `.bin.tmp`): the Vulkan driver's pipeline cache (driver blobs; saved with a size + checksum trailer, and a file that is damaged, too large or from another GPU is ignored at start-up: `[r2rsx] vk pipeline cache: ... is <why>, starting empty`)
  - `rpcs3\shaders_cache\r2_gpu_stamp.txt`: the GPU and driver that cache was built for
  - `rpcs3\shaders_cache\shaderscan.stamp`: makes the launcher run shaderscan again on the next Play (see below)
  - `rpcs3\shaders_cache\r2_pipelines.foz`, `r3_pipelines.foz`: Fossilize databases (`R2_FOSSILIZE`)
  - `vk_pipeline_cache.bin`: the native renderer's Vulkan pipeline cache

  Kept: `rpcs3\shaders_cache\pipelines\vulkan\...\*.bin` and `raw\*.vp` / `*.fp` (RPCS3's pipeline list and shader programs: what gets rebuilt) and the native renderer's `vk_pipeline_variants.bin`, `rsx_engine_programs.bin` and `pipelines_*.db` lists.
- **GPU or driver change:** `r2_gpu_stamp.txt` records vendor, device, driver version, pipeline cache UUID and GPU name when the driver cache is saved. When they differ at start-up the log says `[r2rsx] vk pipeline cache: GPU or driver changed since the cache was built (was: ..., now: ...)`, the old `vk_pipeline_cache.bin` is deleted and every pipeline is rebuilt from the kept list (before play with the option on).
- **Offline shader scan:** [shaderscan](https://github.com/miroslavdanutalexandru-alt/shaderscan) (GPL-2.0, its own repository) is downloaded by Setup / `build.bat` into `tools\shaderscan.exe`: `tools\get_shaderscan.ps1` fetches the release pinned in `tools\shaderscan.version` and checks its SHA-256 (offline: skipped; set `SHADERSCAN_EXE=<path>` to use your own build). It is not part of the port's source or Setup, and the launcher works without it. When `shaderscan.exe` is next to `Launcher.exe` (or in `tools\`), Play first runs `shaderscan --check --out shadercache\rpcs3\shaders_cache`; if that says the cache isn't seeded (first launch, a new shaderscan version, or after Rebuild shader cache), it runs `shaderscan --game <folder> --out ... --progress`, which extracts every RSX shader from your game files into the cache so Compile shaders before playing covers the whole game without a playthrough. The launcher shows a progress panel (Esc or **Skip for now** stops it; the game starts either way) and logs the tool's output to `logs\shaderscan.log`. It runs at most once per launcher session.
- **Pipeline seed:** `tools\pipeline_seed.bin` lists the shader pipelines the game only creates in play (shader hashes and render state, no shader code and no game data). Each start copies the missing ones into `shadercache\rpcs3\shaders_cache\pipelines`, so Compile shaders before playing also builds them and a first visit to an area no longer skips draws (purple / green patches) while they compile. Their shaders come from your own game files through shaderscan; without it they are skipped. `PORT_PIPELINE_SEED=0` turns it off. Release builds refresh it with `scripts\export_pipeline_seed.ps1 -Merge` after a playthrough.
- **Object motion vectors** (`RSX_DLSS_OBJMV`, default Off, Compatible renderer): DLSS/FSR get per-object motion for moving characters and objects (sharper, less ghosting on them) at some CPU cost; Off = camera motion only.
- **Velocity pipeline prewarm** (`RSX_DLSS_OBJMV_PREWARM`, default 1; `0` = old): with object motion vectors on, a skinned character's velocity pipeline is queued the first time it is drawn (not once it starts animating), and these pipelines are built on 2-4 threads instead of one. Before, at a cutscene start (the realtime intro's close-up face) the characters had camera motion only until their pipelines were built, so DLSS smeared the animating face for the first second or two. Log: `objmv onepass prewarm: ...` (once).
- **Camera motion before confirmation** (`RSX_AA_EXACT_UNPROVEN`, default 1; `0` = old): when the per-draw camera vote fails, DLSS/FSR camera motion comes from the game's own view-projection (shared by at least 40 % of the draws) even before the draws have confirmed it. Before, the first ~30 s of a level often ran with zero camera motion (ghosting, smearing, boiling). Log: `camera exact: ... (N where the vote failed, M unproven)`.
- **Camera motion check against depth** (`RSX_AA_MV_CONFIDENCE`, default on; `0` = off): a 64 x 36 grid of the frame's depth is reprojected with the chosen camera motion and compared with the previous frame's depth (read back 4 frames later, `RSX_AA_MV_CONFIDENCE_LAG`). When more than 35 % of the samples are off (`RSX_AA_MV_CONFIDENCE_BAD`) and no motion would fit clearly better, camera motion is zeroed (one history reset) until a check passes. Log: `camera MV confidence: N checks, M rejected ...`.
- **History-reset rate limit** (`RSX_AA_CUT_PARALLAX_GAP`, `RSX_AA_MV_CONFIDENCE_GAP`, frames; R3 defaults 0 = off and 120, R2 uses 120 for both): a parallax-only camera cut or a new camera-motion reject run resets the DLSS/FSR history only when the last reset of the same kind was at least that many frames earlier (held-back triggers do not extend the window). A held-back parallax cut keeps the voted camera motion only with a clear vote majority (else the last trusted motion while at most `RSX_AA_VOTE_HOLD` frames old, then none) and is reset anyway, at most once per gap / 4 frames (deferred, not dropped, inside that window), if the depth check of its voted motion (`RSX_AA_MV_CONFIDENCE`) finds at least 70% of the samples off with the voted motion and with no motion (a real cut). `RSX_AA_CUT_PARALLAX_GAP` is opt-in for R3 if its log shows repeated `rule parallax` resets. Confidence rejects held back by the gap are deferred (reset as soon as the gap allows while the rejects go on), not dropped. `RSX_AA_CONF_CUT=1` (opt-in, default 0): every depth-check verdict is also tested for a real camera cut (at least 70% of the samples off with the applied motion and with no motion, the parallax test) and resets the history at once, gap or not; log: `... N cut resets (RSX_AA_CONF_CUT 1)`.
- **Smoke / dust / sparks under DLSS** (`PORT_DLSS_BIAS_MASK`, default `0` = off in this port; `1` = on, opt-in: in Resistance 3 it caused blotches on some surfaces): blended, non-depth-writing effect draws into the scene before the upscaler (about 25 per frame in R3 gameplay) are redrawn into a coverage target that goes into the DLSS bias-current-colour mask (`PORT_DLSS_BIAS_MASK_VALUE`, default 0.6). Before, DLSS accumulated animated sprites into a flat smear while the camera was still and the real smoke popped in when the camera moved. Log: `PORT_DLSS_BIAS_MASK: N effect draws redrawn, ... mask used in F frames`.
- **DLSS / Frame Generation camera motion** (all default `1`; `0` = the old behaviour): `RSX_AA_DEJIT_SIGNED` removes the camera jitter from motion vectors with the correct sign (fixes dark blotches on rugs and floors); `RSX_AA_EXACT_ALL` picks the camera from all matching vertex programs; `RSX_AA_CONF_TRUST_EXACT` trusts a confirmed exact camera instead of rejecting it as uncertain (less wobble when turning).
- **Light-volume stencil jitter** (`RSX_AA_OCC_JITTER_STENCIL`, default 1; `0` = old): the stencil-marking light volumes (no colour, depth test, stencil on) that test against a copy of the jittered scene depth get the copy's sub-pixel shift, like the occlusion probes (`RSX_AA_OCC_JITTER`). Before, on some jitter phases a volume face crossing a surface at a grazing angle marked a different band: a one-frame hatched light leak on a static sun patch every few frames. Log: `occlusion probes given their depth copy's jitter (RSX_AA_OCC_JITTER): N (S stencil-marking light volumes, ...)`.
- **Decal depth bias follow (`RSX_DECAL_ZBIAS_FOLLOW=0` to opt out).** A biased decal pre-pass whose EQUAL material redraw is never found stops being biased only after 3 misses on different frames (misses while the decal table overflowed, this frame or, for a redraw after the frame boundary, the previous one, are not counted). The mark expires after 600 frames, a matched redraw clears it, and the table is cleared after 60 frames without decals (loading screens), so reused addresses don't inherit it.
- **Decal pairing by content (`RSX_DECAL_ZBIAS_PAIR=1` to opt in; `=2` learns and logs only).** Off by default. Pairs a depth-writing quad of the scene pre-pass with the depth EQUAL quad that redraws it in the material pass by the bytes of its positions and the transform constants both vertex programs read, instead of the buffer address (R3 moves the vertex buffers between the passes). After 8 frames in a row where every pre-pass draw of that content got exactly one paired redraw, both draws get the same `RSX_DECAL_ZBIAS` depth bias (the R3 poster edge). A biased draw whose redraw does not come blocks its content for 600 frames. The log line "decal pairing" counts paired / unpaired redraws, learned keys and biased draws.
- **Decal depth bias EQUAL guard (`RSX_DECAL_ZBIAS_EQGUARD=0` to opt out).** The decal pre-pass bias is applied only in forward-rendered scenes: no depth-EQUAL no-write draw of any size in the last 120 display frames (the 120 frames restart on every frame of boot and of any loading screen, however long). The material pass batches the redraws of pre-pass quads (12 to 3000+ indices), so they can't be matched to a biased quad; their EQUAL test then fails and the pre-pass normals show as neon-green floor, foliage and poster patches. The 5 s `decal bias:` line counts the pre-pass draws held unbiased and the EQUAL draws seen.
- **Deformed-mesh motion carry** (`RSX_DLSS_OBJMV_DEFORM_CARRY`, default 1; `0` = old): CPU/SPU-rewritten meshes updated every other frame are also copied on the unchanged frame, so the next change has a previous copy. Log: `objmv2 detail: ... deform carried N, fallback: no previous copy A, layout B, history C; not copied D`.
- **Deformed-mesh motion, every gap** (`RSX_DLSS_OBJMV_DEFORM_CARRY` is now a frame count, default 12, `0` = off, `1` = the old one-frame carry; `RSX_DLSS_OBJMV_DEFORM_MB` 48 / `_MAX` 384, clamp 1024): a deformed mesh that last changed up to N frames ago is still copied each frame, so animations that update every 2-12 frames keep a previous copy ("no previous copy" fallbacks were ~20 draws/frame at the diner).
- **Camera vote by object** (`RSX_AA_VOTE_OBJECT`, default 1; `0` = old far-plane screen metric): two draws agree when their object origin and unit axes land within the vote tolerance, as om_pick_nearest tests. The far-plane test amplified float noise, so only ~7-11 of ~1300 diner draws agreed and every frame fell back to an unconfirmed camera exact. Log: `camera vote: ... agreeing`.
- **Separate budget for draws without depth writes** (`RSX_AA_EVALS_NOWRITE`, default 384; `-1` = old shared `RSX_AA_EVALS` cap): transparents and particles can no longer use up the 2048 capture budget before the opaque draws are captured.
- **Unchanged-constants static path** (`RSX_DLSS_OBJMV_FAST_STATIC`, default 1; `0` = off): a rigid draw whose constants differ from its previous-frame pair (or another occurrence of the same draw) only in the shared camera rows is static without running the vertex-program interpreter twice. The result is the same; it costs less CPU. Log: `objmv pairing: ... N by unchanged constants`. The loose key (`RSX_AA_MATCH_LOOSE`) is no longer hashed for skinned programs, which never read it.
- **Review fixes (round 2)**: the unchanged-constants static path now also requires this draw's camera rows to equal this frame's camera (the rows `om_exact_ref` last proved separate from the whole transform), so an object that sat at identity last frame and moves now is no longer called static. 1 in 16 fast hits still takes the full path (log `+ N sampled full checks`). The draw keys and their per-frame ordinals (strict and loose) are now made for every scene draw before the `RSX_AA_EVALS` / `RSX_AA_EVALS_NOWRITE` budget test. The budget only gates capture, so the draws it cuts no longer shift the pairing of later draws with the same key.
- **Deferred classification, A/B** (`RSX_AA_OBJMV_DEFER`, default 0; `1` = worker thread; `2` = render thread at the flip): a matched rigid draw that was static last frame (paired, no own motion, no skin or deform history) is predicted static at draw time and classified after the scene. If the prediction misses (the object started moving), that frame gets camera motion and the object's history capture starts on the next frame. These misses are counted as `late-start`. Log: `objmv defer (RSX_AA_OBJMV_DEFER=N): ... late-start N ...; fast exit (RSX_AA_FAST_EXIT) N of M draws`. Compare it with the `objmv cpu` line.
- **Non-scene fast exit** (`RSX_AA_FAST_EXIT`, default: on with `RSX_AA_OBJMV_DEFER`; `1` / `0` = force): a draw outside the scene surfaces whose targets and depth/stencil/colour state match the previous draw that needed nothing returns from the DLSS draw hook first, without other work. Any state change (surface bind, section, readback, depth clear, flip) invalidates the cache.
- **Draw-hook profile** (with `R2_RSX_PROF=1`): every stats window logs `r2aa_on_draw split (R2_RSX_PROF): N draws/frame (S scene, F fast exit); us/frame: head, scene keys, capture, classify, tail, fast exit; ns/draw`. AA runs fired inside the hook are excluded. The jitter bookkeeping per jittered draw (`jd_depth` / `jd_shift`) and the depth-latch lookup (`RSX_AA_DS_LATCH`) now reuse the previous draw's entry when the target is the same, instead of hashing again; the results are unchanged.
- **Camera vote sampling** (`RSX_AA_VOTE_SAMPLE`, default 1024; `0` = every captured draw): the vote reads at most this many evenly strided draws.
- **Alpha-to-coverage** (`RSX_AA_A2C`, default `stable`; `noise` = RPCS3's screen-fixed noise; `hashed` = opt-in, shared with R2): with FSR/DLSS on, MSAA is off and A2C is emulated per pixel. `stable` is a fixed 0.5 cutoff (no boiling, but stair-stepped foliage, fence and hair edges). `hashed` (aliases `hash`, `2`) uses Wyman & McGuire's hashed alpha test: the threshold is a hash of the object-space vertex position in cells about one render pixel wide, so the pattern sticks to the surface (no swimming like a screen-space dither, and no frame-index term that DLSS would treat as noise); the upscaler's sub-pixel jitter lands on neighbouring cells and DLSS/FSR accumulate a soft edge. Alpha 1 always passes, 0 always fails, and the alpha test still runs first. A vertex program that does not read attribute 0 gets the plain 0.5 cutoff (no stale vertex-layout read). Trade-off: thin distant foliage can shimmer slightly where `stable` is clean but aliased, so `stable` stays the default. Logged as `[r2rsx] RSX_AA_A2C=hashed: alpha-to-coverage program #N ...`. `RSX_AA_A2C_MIPSCALE=<k>` (default 0 = off; try 0.25) also scales the alpha of 2D texture samples in A2C shaders by `1 + mip * k`, so minified foliage keeps its coverage at a distance (it touches every 2D sample of those shaders, hence opt-in). Unit test: `test_r2_a2c_hashed`.
- **Distant cut-out foliage** (`RSX_AA_ATEST_MIPSCALE`, default off in R3, R2 default `0.15`; try `0.15`-`0.25`): GEQUAL/GREATER alpha tests on minified texels compare `alpha * (1 + mip * k)` (coverage-preserving mip alpha, cutoffs above 0.3 only), so thin leaves do not vanish in the mips and boil in the distance. Only programs whose output alpha comes from exactly one 2D texture, and only jittered main-scene draws (not shadow maps). Mip 0 and the written colour are unchanged.
- **RSX memory tiling** (`RSX_TILING`, old name `R2_RSX_TILING`; default on, R2 parity): "Handle RSX Memory Tiling" is forced on by the renderer even when an older, user-edited `rpcs3_config.yml` (kept by `tools\update.ps1`) still has it off; without it the aim-down-sights / DOF main-memory targets are read raw (striped garbage). The native GCM path (`project\main.cpp`) follows the same rule. `RSX_TILING=0` turns it off. Logged as `[r2rsx] tiling: Handle RSX Memory Tiling on (default, ...; yml on|off)`.
- **Render-target CPU authority** (`RSX_RT_CPU_AUTH`, default on, shared with R2; `0` = RPCS3 behaviour): once a colour surface has been read back to guest memory and not drawn to since, a sample that reinterprets it in another format is decoded from guest memory, so CPU/SPU writes after the readback are seen. RPCS3's 3-sample memory tag misses SPU writes that leave those samples unchanged (the aim-down-sights blur showed a checkerboard). Logged as `[r2rsx] RSX_RT_CPU_AUTH #N: ... decoded from guest memory` (rate-limited). Unit test: `test_rt_cpu_auth`.
- **Tiled texture reads from guest memory** (`RSX_DETILE_GUEST_SRC`, default on, shared with R2; `0` = RPCS3 behaviour): textures and render targets loaded from main memory (tiled or not) read a copy of guest memory taken when the work is recorded, not the renderer's shared DMA mirror, and the upload heap holding those copies is kept until the frame using it has finished on the GPU. Render-target readbacks still in flight (aim-blur early readbacks, fault copies) rewrite that mirror on the GPU afterwards, so the aim-down-sights blur layer could show the old light buffer as purple/black bands, worst while firing.
- **Protect before the guest-memory copy** (`RSX_GUEST_SRC_MMFLUSH`, default on; `0` = off): before that copy is taken, the page protection the texture cache queued for the texture is applied, so a game/SPU write landing between the copy and the GPU submit faults and re-uploads the texture instead of leaving a half-written copy cached. This also covers the CPU decode path (all guest-memory sources of an upload are flushed once before they are read). It is race hardening, not the splash fix below.
- **Linear textures decode on the CPU** (`RSX_TEXDECODE_LINEAR_CPU`, default on; `0` = GPU decode for linear textures too): linear (non-swizzled) uploads from guest memory byteswap on the CPU instead of the zero-copy scratch buffer + compute shader; swizzled uploads keep the GPU deswizzle. With the GPU path the Resistance 2 boot splash (1280x720 linear D8R8G8B8) intermittently lost its text and only the loading icon showed; `RSX_GPU_TEXDECODE=0` alone fixed it.
- **Failed pipelines** (log only): a pipeline whose link failed (a driver fault caught by the compiler) keeps its placeholder, so its draws are skipped for the rest of the session and it is never relinked; this is now logged once per pipeline in the RPCS3 log (`rsx_log` error `Pipeline link failed (vp id = N, fp id = M): its draws are skipped for this session`, written by the compiler thread with the real result; a pipeline that is merely queued for an async compile is not reported). Draws are skipped only *temporarily* while a new pipeline compiles asynchronously.
- **Graphics feature trace** (`RSX_FEATCOV`, default off since it costs about 2.5 ns per RSX method write; `1` = on; shared with R1 / R2): every RSX method, render state value and shader op the game uses is listed once in `run.log` as `[featcov]` lines, each marked with what the renderer does with it (real / noop / ignored / unhandled). Dumps every `RSX_FEATCOV_SEC` seconds (default 60; only newly seen items; `0` = only at exit) and at exit. Summarise with `python scripts\featcov_report.py run.log`.

## RPCS3 patches

The community RPCS3 patches for Resistance 3 (RPCS3's `patch.yml`) were checked against this game's program file: disc **BCUS98176 / BCES01118 1.00**, PPU hashes `502feb2351d2b637a2704d5a50cb44bc1b781532` (US) and `2701cf372814d59f26e771dc9394323d4f799682` (EU), which share every address. ## Performance work

Performance fixes have been applied as far as possible without changing how the game looks:

- **SPU (the PS3's job processors):** faster lock-line reservation and acknowledgement, cheaper waits on SPU channels and direct block-to-block jumps in the translated SPU code (`SPU_FAST_LLAR`, `SPU_FAST_ACK`, `SPU_FAST_WAIT`, `SPU_FAST_HOP`: all on by default, `=0` turns one off for testing; `SPU_FAST_LLPOLL=<n>` is a back-off for lock-line polling, on by default (`<n>` pauses per re-read, default 8; `=0` off)). `PORT_SPU_SPINWAIT=old|backoff|wait` sets how a raw SPU spins in a blocking channel wait before it sleeps: the default is `wait` (picked by `PORT_NOSPIN`, with a pause-only spin; `old` with `PORT_NOSPIN=0`), `old` is the original tight spin, `backoff` uses growing pause bursts and then yields the core after 20 µs, `wait` also sleeps after `PORT_SPU_SPINWAIT_US` (default 20); `backoff` is experimental (no measured gain); `[spuwait]` lines every 10 s show waits, waits finished while spinning, sleeps, yields and wake-ups.
- **`PORT_NOSPIN=1|auto|0`** — the no-spin wait profile. Default `1` (on for every CPU); `auto` = on only below 12 logical CPUs; `0` (or `off`) = the old spinning waits. It sets the default of: `SPURS_TARGETED_WAKE` (SPURS wakes only the SPU that has work), `PS3_USLEEP_PARK` (short `sys_timer_usleep` waits park instead of spinning), `PORT_SPU_SPINWAIT` (`wait` instead of `old`, pause-only spin) and `R3_JOBWAIT_WAKE` (job waits are woken instead of polled). Setting any of these explicitly overrides `PORT_NOSPIN` for that one. Logged as `[nospin] on|off`.
- **`PORT_SPU_SPIN_ADAPT=<percent>`** — adaptive SPU wait spin (adapted from the inFAMOUS 2 PC port, MIT). Each SPU thread tracks how often its pre-sleep spin ends with the channel ready, and skips the spin while that share is below `<percent>`. Every 8th skipped wait spins anyway to measure again. This stops an idle SPU (menus, pause, a sleeping sound engine) from spending its spin window on every wait, which matters most on 4-core CPUs. Default `25`; `0` = spin on every wait as before. Logged as `[spuwait] adaptive spin`.
- **`PORT_CORE_SCARCE=0|1`, `PORT_CORE_SCARCE_BELOW=<n>`** — "few cores" detection: physical cores (SMT siblings counted once) in the process affinity mask, below `<n>` (default `6`) = scarce. Logged as `[cores]`. `0`/`1` forces it. Shared with Resistance: Fall of Man, where it picks the event-woken RSX frame clock; here it is only reported.
- **Spin-waits:** the game's main-thread loops that spin while waiting for SPU jobs execute a CPU pause hint each lap instead of hammering the core (`R2_SPIN_PAUSE=0` turns it off), and give the core away on CPUs with few threads: every 8th lap there, with pause hints in between (`R3_SPIN_YIELD_EVERY=<1-64>`, default 8; `1` = give it away every lap, the older behaviour).
- **Short sleeps:** the runtime's 1 ms naps (SPU interrupt and mailbox waits, SPU group start, SPURS job-guard and queue waits, timed mutex locks) use a high-resolution waitable timer, which wakes after about 1 ms instead of at the next 1–2 ms scheduler tick (`PORT_HIRES_SLEEP=0` = plain `Sleep(1)`).- **Memory faults:** the handler that commits guest memory on first touch looks up a bitmap instead of asking Windows, which makes the common case much cheaper.
- **Measured (in-game bench, Haven, RTX 5070, 60 fps target, DLSS 1080p → 4K):** 44 fps at first, limited by the RSX thread (ZCULL report waits cost 8.5 ms per frame); with relaxed ZCULL and deferred labels 55 fps, ZCULL down to 0.24 ms per frame. The remaining costs were framebuffer-bind locking, shader-program lookups and FIFO command processing; the program lookups were cut since (re-sent programs kept, previous pipeline reused), and Resistance 2's renderer rounds 4 and 5 (framebuffer-bind memory protection, texture-cache readbacks) are included. Latest bench: **59.5 fps** in Haven (1,145 draws per frame) at about 10.5 µs of RSX-thread time per draw (from 19.7 at first), stable over a 12-minute session; the DLSS per-draw hook went from 2.9 to 0.2 µs. Lower per-draw cost helps low-end CPUs the most.
- **Network thread:** the game's HTTP thread polled `cellHttpClientPollConnections`, which wasn't implemented and returned at once, so it used a whole CPU core; it now waits for a connection like the real function, and with no connection returns the library's "no connection" error so the thread sleeps between polls.
- **Renderer:** thread counts sized to the CPU, idle back-off in the RSX threads, frame pacing mirrored into RPCS3's vblank, skipped redundant render-target write-backs, relaxed ZCULL by default (no GPU stalls for occlusion results; strict mode batches reads, sleeps on the GPU fence and defers labels), shader-program lookups that skip re-hashing (`R2_PROG_HINT`, `R2_PROG_MRU`), re-sent fragment and vertex programs kept instead of analysed and looked up again (`R2_FP_REBIND`, `R2_VP_REBIND`) and the previous draw's pipeline reused when only state changed (`R2_PIPE_MEMO`), fewer and cheaper `VirtualProtect` calls (`R2_MM_SKIPSAME`, `R2_MM_INCR`), no blocking GPU readback of render targets that a new target fully overwrites (`R2_FBO_COMMIT_FLUSH`), deferred ZCULL labels carried over a flip in strict mode (`R2_ZCULL_FLIP_LAG`), cheaper DLSS camera-matrix matching, and fewer DLSS resets (see the table above). Round 8 (after Resistance 1's own renderer): unchanged transform constants and repeated index ranges are not uploaded again (`R2_XFORM_MEMO`, `R2_IDX_DEDUP`), the shader preload is logged (`R2_SHADER_PRELOAD`), and `R2_RSX_PROF=1` prints where the end of each draw goes (`r8` lines: Vulkan recording, uploads, pipeline misses, FIFO redundancy); `R2_RSX_CENSUS=1` adds a usage census.
- **Native replacements at a glance:** one start-up log line lists which native (hand-written C/C++) replacements are on and which are off, with the switch that controls each, in the same format in all three Resistance ports: `[native] on: hot-ppu(R3_HOT_NATIVE) spu-jobs(R3_NATIVE_JOBS) audio-jobs(R3_NATIVE_AUDIO_JOB) dof-kernels(R3_NATIVE_DOF) edge-zlib(PORT_NATIVE_EDGE_ZLIB) bink-idct(R3_NATIVE_JOBS) detile-fast(RSX_DETILE_FAST) spu-sched(PORT_SPU_SCHED) dof-job(R3_NATIVE_DOF_JOB) dof-gpu-approx(R3_DOF_GPU_APPROX)` (edge-zlib and bink-idct are kernels of spu-jobs, as in R2). The spu-jobs, edge-zlib, bink-idct and audio-jobs entries show what the gates will really do (off when the switch is off, a mask bit is clear, a self-check disabled the kernel, or this build's lifted code has no hook for it). As in R2, an entry whose own switch says otherwise is labelled `,overridden` with the reason, e.g. `edge-zlib(PORT_NATIVE_EDGE_ZLIB,overridden: hook missing)`. Some audio kernels masked off show as `audio-jobs(R3_NATIVE_AUDIO_JOB,partial: kernels 0x3 of 0x7F)`. On/off switches take `1/on/true/yes` and `0/off/false/no` (any case, surrounding spaces ignored) in the modules and in this line alike; anything else (including other numbers) keeps the default. A build without lifted SPU code shows them all off. The module-specific lines (`[hot]`, `[native-jobs]`, `[ndof]`, `[naudio]`) follow with the details.

### CPU switches and builds

In heavy scenes the frame rate depends on the game's main PPU thread and **rawSPU0**, the SPU job kernel (the main thread waits on its jobs in `func_0082C190`). Env switches (unset = default):

- `PORT_SPU0_CPU=<n>`: pins rawSPU0 to logical CPU n with an empty SMT sibling, like the main thread (`PORT_MAIN_CPU`, default 2) and the RSX thread (`PORT_FIFO_CPU`, default 4). Off by default: Resistance 3 runs all SPU work through SPURS and never creates a raw SPU, so the core reserved for it (CPUs 6/7 on 6C/12T) used to sit idle while the six SPURS lanes shared 3 cores. Without it the rest mask on 6C/12T is `0xFC3` (4 whole cores) instead of `0xF03`. `PORT_SPU0_CPU=6` restores the old reservation on 6C/12T and 8C/16T (on 12+ cores without SMT the old default was CPU 3). In the Compatible (RPCS3) renderer that RSX core goes to the thread named `rsx::thread`. `-1` turns this off, and `PORT_MAIN_CORE=0` turns off all pinning. Each pin is logged as an `[affinity] ... pinned` line.
- `PORT_CPU_PCORES=off` (launcher: Advanced > CPU threads > Prefer P-cores): on Intel hybrid CPUs (P + E cores, 12th gen and newer) the main guest thread, raw SPUs, SPURS lanes, the RSX FIFO / render / engine threads (`rsx::thread`, FIFO walker) and the audio mixer get P-core thread CPU sets (`SetThreadSelectedCpuSets`; a thread runs only where its sets and its affinity overlap) and EcoQoS off, as many of them as the usable P-cores allow (about two hot threads per P-core: main and FIFO from 2, render / engine, raw SPU 0, lanes 0-2 and the mixer from 4, raw SPUs 1-3 from 6, lanes 3 and up from 8; fewer than 2 = nothing). Usable = P-cores inside the process affinity, or, while the core keeper hard-pins main / FIFO / raw SPU 0 (12+ logical CPUs), inside the mask it leaves for the other threads; the threads it pins get no CPU sets. Other threads are left to Windows (Resistance 2 / 3 with 4+ usable P-cores: the process default CPU sets are the P-cores too). CPUs whose cores all share one efficiency class (AMD, multi-CCD included, older Intel) are not changed. Default on; `off`/`0`/`false`/`no` turns it off; `PORT_PCORE_HOT=0` is the older name. `PORT_THREAD_PLACEMENT=off` also turns it off. Log: `[cpu] hybrid CPU ...` or `[cpu] P-core placement off (<why>; ...)`, and `pcore-pin` in the `[native]` line.
- `PORT_LARGE_PAGES` (default off): **not available in this port.** Resistance 1 can put guest memory in large pages; here the Compatible renderer's texture cache write-protects guest memory in 4 KB pages to notice CPU writes to textures, which a large page cannot do, and the guest space is one pagefile section mapped twice. Setting it only makes the `[native]` line say `large-pages(PORT_LARGE_PAGES,overridden: texture cache needs 4 KB page protection)`. (For Resistance 1: Large pages (2 MB instead of 4 KB) cut TLB misses on the game's scattered memory accesses; the gain is small (a few % at most, CPU-bound scenes only). Windows gives them only to an account with the **Lock pages in memory** right: run `secpol.msc` (Windows Pro / Enterprise; on Home use `ntrights -u %USERNAME% +r SeLockMemoryPrivilege` from the Windows Server 2003 Resource Kit, or a policy editor), Local Policies > User Rights Assignment > **Lock pages in memory** > Add User or Group > your account, then sign out and back in (no administrator rights needed afterwards). Without the right, or when Windows cannot find enough contiguous free memory (more likely the longer the PC has been up), normal pages are used and the `[native]` line says why: `large-pages(PORT_LARGE_PAGES,overridden: no privilege)` (or `not enough contiguous memory`, `not supported`).)
- `PORT_THREAD_PRIORITY=on` (launcher: Advanced > CPU threads > Raise game thread priority): the main and RSX threads run at above-normal priority (only raised, never lowered; any CPU). Default off: on CPUs with 4 cores or fewer a raised spinning thread can starve the others. Each changed thread is logged as `[cpu] <thread> (thread N): ...`.
- `PORT_KEEPER_MS=<ms>`: the thread-placement keepers rescan every 1–2 s while new threads appear, then every 5000 ms (default).
- `PORT_PIN_TOPO=0`: the default pin CPUs above (main, RSX) are now taken from the detected CPU topology: the first logical CPU of physical cores 1 and 2 (P-cores first on hybrid CPUs); rawSPU0 has no default pin in Resistance 3, and a set `PORT_SPU0_CPU` is used as given. On a 6-core/12-thread CPU that is still 2 and 4; on CPUs without SMT it is 1 and 2 instead of two hot threads sharing a core. `=0` uses the old fixed 2 / 4. The `[affinity] main thread ...` line shows the CPUs and the switch values.
- `PORT_REST_SMT=<0|spu0|1|2>`: where all other threads (SPURS lanes, rawSPU1, RSX workers, driver, audio) may run. `0` (default): only cores that have no pinned hot thread, so every hot thread keeps its SMT sibling idle (on 6C/12T that is mask `0xFC3`). `spu0`: also the sibling of the rawSPU0 core when `PORT_SPU0_CPU` is set (the Resistance 2 default, where rawSPU0 mostly polls). `1`: also the siblings of the rawSPU0 and RSX cores. `2`: also the main thread's sibling. Try `spu0` or `1` if the `[thrcpu]` lines show the SPURS lanes starved; it costs the hot threads some SMT throughput.
- `SPU_FAST_LLPOLL=<n>`: an SPU that re-reads an unchanged lock line (GETLLAR) more than `SPU_FAST_LLPOLL_AFTER` times in a row (default 64) is polling, so each further re-read first executes `<n>` CPU pause instructions (default 8, about 0.1 µs). A tight poll slows the thread on the other half of the same core by ~1.6x; with the pauses that drops to ~1.18x. The poll still sees a write on its next read. `=0` turns this off. Logged once as `[spu-llpoll]`.
- `PS3_USLEEP_NOTIFY_PUT=0`: a short guest `usleep` poll (under 1 ms) already ends early when an SPU atomic writes guest memory (`PS3_USLEEP_NOTIFY`). It now also ends early on a plain SPU DMA PUT, so the main thread's SPU-job wait re-checks as soon as a job writes its result instead of finishing its sleep. It costs nothing while no thread is waiting. `=0` turns this off. Logged once as `[usleep] PS3_USLEEP_NOTIFY=1 PS3_USLEEP_NOTIFY_PUT=1 ...`.
- `PORT_SPU_SCHED=0`: an SPU job that waits for another job or the PPU to change a shared memory line (lock-line reservation wait: SPURS job queues and locks) is woken by every write that goes through the runtime's coherence path. A write that bypasses it was only noticed on the next 10 ms poll; such waits now re-check the line every `PORT_SPU_SCHED_MS` (default 1, 1–10), so a missed wake costs at most about 1 ms. Waits only end when their condition holds, as before; other channel waits are unchanged. Logged once as `[spu-sched] PORT_SPU_SCHED=1 ...`, and every 10 s as `[spu-sched] 10s: lost-reservation sleeps=... missed wakes=...` (missed wakes = sleeps that timed out with the line already changed). `=0` restores the 10 ms poll. With `PORT_SPU_SCHED_STATS` (default on; `=0` off) the 10 s line also gives the total and average time asleep, how many sleeps ended on the timeout instead of a writer's wake, the sleeps and time per SPU image, and the line of the last missed wake (to find the writer that bypasses the coherence path). Shown as `spu-sched(PORT_SPU_SCHED)` in the `[native]` line. Offline test: `ps3recomp\runtime\spu\tests\test_spu_sched_wake.c`.
- `PORT_NOTIFY_ALL_WRITES=1` (experimental, **default off** since 2026-11-17): the RSX's own writes into game memory (semaphore labels, report and zcull results, blits and inline images, surface flushes back to game memory, the async aim-blur readback serve) also wake an SPU job waiting on a memory line they touch, instead of the job finding out on its next re-poll. The check is a bitmap scan of the written range, so writes to lines no SPU job ever waited on cost almost nothing. It was on by default for one test round, which brought back the one-frame black screens while firing in aim-down-sights (with 22 repeated aim-blur label stores against 1–7 in earlier runs), so it is off until an A/B clears it; without it, such a job notices the write on its next `PORT_SPU_SCHED_MS` re-poll. With it on, the `[spu-sched]` line counts these wakes as `range-notify wakes`.
- `RSX_FIFO_RETURN_CAPTURE` (aliases `R3_FIFO_RETURN_CAPTURE`, `R2_FIFO_RETURN_CAPTURE`; default on, `0` = off): fixes FIFO desyncs (`[fifo] desync #N`, lost or corrupted frames) when the RSX thread is CPU-bound, for example R3 at the diner at 30-38 fps. The game links a short command segment into the ring and ends it with a JUMP back to where it came from. It waits until GET == PUT at the segment end, moves PUT, and soon reuses the segment memory. A late RSX thread then runs data as commands. The puller now remembers that return JUMP while it waits at PUT and runs it if the word was reused before it saw PUT move. It only overrides a word reused as data or a method header. If the game rewrote the segment end with its own JUMP, CALL or RET, that live word runs. It also requires PUT to be near the ring the JUMP returns to. A loop detector turns the capture off for the session if, after a substitution, the RSX jumps to the same place again before it reaches PUT while PUT stands still. It then resumes at the segment end if the game has re-linked it there with its own JUMP or CALL, so the live word runs and nothing is skipped. Otherwise it resumes at PUT and skips the commands up to PUT. It also clears the restore point and CALL return left in the old lap, and logs `[fifo] return-capture loop: ...`. The detector uses progress, not time, so long semaphore waits never trigger it. GET publication is unchanged. `[fifo] return-capture #N` lines count the saves. Desyncs also print `[fifo-diag]` lines in both games (`R3_FIFO_DIAG=0` = off).
- `R3_NATIVE_JOBS=0`, `PORT_NATIVE_EDGE_ZLIB=0`: native SPU job kernels, the same scheme as R2's `R2_NATIVE_JOBS`. Kernel 0 is Edge zlib `inflate_fast` (the decompressor used for level and asset streaming), which runs as native host code instead of the lifted SPU code. It is byte-exact against the lifted code offline (0 mismatches over 1550 raw and 1400 chunked streams plus 25k fuzzed states). The whole decompress call is 1.9× faster and `inflate_fast` alone 4.1×. It also checks itself while the game runs: the first 8 calls and then every 4096th (`R3_NATIVE_JOBS_CHECK=<n>`, `0` = off; `R3_NATIVE_JOBS_VERIFY=1` = every call) run the lifted code on the real state and the native code on a copy, and compare the local store and r0/r1/r80–r127. The game keeps the lifted result of a checked call. A mismatch is re-run once on the same input, and if it repeats the kernel is turned off for the rest of the session (logged once as `[native-jobs] edge_zlib MISMATCH ... kernel DISABLED`; a mismatch that does not repeat is counted as a race). On start it logs `[native-jobs] edge_zlib (LS 0x8100) native ON (self-check: first 8 calls, then 1/4096)`. Kernels 1–3 are the movie decoder's (job 421, Bink video) 8×8 dequantise + inverse-DCT block routines (put, 2× put, add-to-reference; `project\r3_native_bink.c`, AVX2): byte-exact against the lifted code on 300k fuzzed calls, including the add routine's reference stride 0 (one row reused) (`scratch\native_bink`), 12–17× faster per block, shown as `bink-idct` in the `[native]` line (`partial` when only some are on; off with "needs an AVX2 build" in a `PORT_ARCH=baseline` build). They use the same self-check and auto-disable. `R3_NATIVE_JOBS_MASK` selects the kernels (default `0xF`), `R3_NATIVE_JOBS_STATS=1` prints counters, and `R3_NATIVE_JOBS=0` or `PORT_NATIVE_EDGE_ZLIB=0` runs the lifted code. The kernels' gate calls (4), and the 7 of `R3_NATIVE_AUDIO_JOB`, are hooks in the lifted SPU code that setup's code generator (`tools\r3_regen.py`) puts back from `tools\hooks\spu\<module>.json`. Each hook is checked against the freshly generated text, and generation stops if one no longer fits. `tools\test_spu_hooks.py` checks that applying them reproduces `project\spu` exactly. A build whose lifted code lacks a hook logs `[native-jobs] ... native OFF: hook missing` and shows the kernel off.
- `SPU_INLINE_CH=0`: by default the lifted SPU code writes the MFC DMA parameter channels and reads the status channels inline instead of calling the channel runtime. `=0` restores the runtime calls. The build option is `-DPORT_SPU_INLINE_CH=OFF`.
- `R3_OCC_SKIP=1` (default): occlusion-query results (same as R2's `R2_OCC_SKIP`). Only used with `R3_OCC_BLOCKING=0`: when last frame's GPU occlusion results are not ready yet, that set is drawn visible once instead of waiting (never hidden; a little extra drawing), and the game waits normally on the next frame, so the CPU and the renderer work in parallel. `=0` waits every frame. **`R3_OCC_BLOCKING=1` (the default since 2026-11-12) is the old (0.2.3) blocking wait exactly**: with relaxed ZCULL (now also R3's default) it measured no popping and 52.5 → 55.1 fps; `=0` selects the non-blocking skip, `=2` blocks with the native capped wait. Setting `R3_OCC_SKIP` or `R3_OCC_WAIT_US` explicitly makes the blocking default 0. `R3_OCC_WAIT_US=<n>` caps the wait at n µs (default `50000`). Logged every 10 s as `[occ]`. In R2 the skip took a heavy fight from 35.7 to 46.1 fps, but with relaxed ZCULL it made objects pop.
- `RSX_FIFO_GET_DEDUP` (default on; `0` = always store): the FIFO puller skips publishing GET when the guest-visible GET already holds that value (run_FIFO publishes after every packet, ~60k times a frame, mostly the same cache end while the puller lags PUT). Guest memory stays identical; it saves the redundant stores to the control line the guest polls. `[fifo-get]` (with `[fifo-merge]`, every 5 s) prints stores/f vs identical skipped/f.
- `RSX_FIFO_NOP_LAZY_TS` (default on; `0` = upstream): a FIFO NOP no longer reads the clock (QPC) twice to time a zero-length idle; the idle start is taken only when the FIFO really goes empty/spins or a reader needs it. The game's stream has tens of thousands of NOPs per frame (the clock reads were 4-5% of the RSX thread). `[fifo] RSX_FIFO_NOP_LAZY_TS=1: N NOP idle entries/s ...` every 5 s.
- `R3_OCC_LATE_LOG` (default on; `0` = off): with the default `R3_OCC_BLOCKING=1`, the occlusion wait hook still counts, log only: `[occ] 5 s: sets N, last report ready when the game asked N (x%), late (game's own wait blocks on the RSX) N; reports of ready sets: visible N, culled N`.
- `RSX_FIFO_INLINE` (alias `R2_FIFO_INLINE`, default on; `0` = off): RSX thread FIFO decode fast path shared with R2. Command headers and arguments that are already in the FIFO cache are read inline, and the method register is stored inline. It runs the same code as the normal path, so the results are identical (`scratch\rsx_thread\fifo_bench.cpp`: 10.9 → 6.8 ns per method, about 0.2 ms per frame at R3's ~53k methods). The main thread waits for the RSX command buffer to drain, so a faster FIFO also shortens that wait. It is listed in the `[native]` line as `rsx-fifo-inline`.
- **Per-draw CPU memos** (renderer, shared with R2): `RSX_SAMPLER_CACHE` (**default on**; `RSX_SAMPLER_CACHE=0` turns it off) reuses the derived sampler settings of a fragment texture unit when every register, format field, LOD bias and anisotropy input is bit-identical to an earlier one. `RSX_VTX_REUSE=1` (experimental, **default off**) skips re-copying an uncached vertex upload when its guest bytes are byte-identical to the same draw's copy already in this frame's vertex ring. Both give exactly the same output and save at most about 0.5 ms per frame in R2's dense fights; R3 draws fewer (about 1,100–1,500 per frame), but its texture-environment load is the larger share of each draw, and a faster RSX thread also shortens the main thread's command-buffer drain wait. With `R2_RSX_PROF=1` the `[r2rsx-prof]` block gets a line with memo hits and reused uploads. Both switches take the `[native]` switch values (`1`/`on`/`true`/`yes`, `0`/`off`/`false`/`no`) and are listed in the `[native]` line as `rsx-sampler-cache` and `rsx-vtx-reuse`.
- `RSX_TEX_SEARCH_MEMO` (default on; `RSX_TEX_SEARCH_MEMO=0` = off) and `RSX_SAMPLER_CACHE_WIDE` (default on; `0` = off): two more exact RSX-thread memos for large outdoor scenes (R3's diner: about 3,000 draws and hundreds of textures per frame, RSX thread CPU-bound at 30-38 fps). `RSX_TEX_SEARCH_MEMO` remembers which cached texture the texture cache's lookup returned for an address, format, size and pitch, and reuses it while no texture section has been created, re-protected, blitted or invalidated since (framebuffer re-locks excepted, they can never answer a texture lookup) and that texture still passes every check the lookup applies; otherwise the full lookup runs as before. `RSX_SAMPLER_CACHE_WIDE` gives the `RSX_SAMPLER_CACHE` memo 16 hashed sets of 4 entries per texture unit instead of 4 entries, which outdoor scenes overflowed (about 600 re-derivations per frame). Both give exactly the same output. The `[texcache]` line ends with `lookups N (search memo M)`: memo-eligible texture lookups and how many the memo answered.
- `RSX_AA_PRECREATE_INIT` (default on; `=0` = at the first flips) and `RSX_AA_PRECREATE_IDLE` (default on; `=0` = create at the 3rd flip as before): DLSS/NGX setup can take about 3 s on the RSX thread. Run inside a flip, the upscaler pre-create (`RSX_AA_PRECREATE`) stalled a label the guest was polling, and R2 printed "GPU sit and spin timeout" at boot (the guest's watchdog gives up after about 2.5 s; the REF register is unused at that point, so its 0xffffffff value is not the cause). With a size file (`r2aa_size.txt`), the pre-create now runs in the renderer's init under the start-up screen, before the guest can queue anything. Without that, the flip-time pre-create waits for a sustained idle FIFO: no flip, no pending commands, deferred labels or zcull reports for `RSX_AA_PRECREATE_IDLE_MS` (default 250) in a row. If that never happens by flip 603, the first scene creates the upscaler. A later size or format change recreates it as before. The `[r2aa]` line says when it ran and how long creation took.
- `RSX_DS_RO_DEFER` (default on; `RSX_DS_RO_DEFER=0` = off): soft particles alternate draws that sample the bound depth (feedback-loop layout) with draws that don't, and each switch cost a depth layout barrier plus a render pass break (about 60 per frame in transparents). A non-sampling draw that writes neither depth nor stencil now keeps the feedback-loop layout and the read-only barrier chain stays elided; the restore runs at the next depth/stencil-writing draw or depth clear. Output-identical (no depth writes happen between the elided barriers).
- Log hygiene: `logs\rpcs3_rsx.log` no longer opens a compressed `.gz` copy (it never worked and left a 0-byte file and a "Log file open failed" line every run; `RSX_LOG_GZ=1` restores it). RPCS3's overlay icons are not shipped, so their absence is one notice instead of about 30 errors. FIFO-recover lines no longer end with a stale Windows error ("Not enough memory resources"). The `[texcache]` line counts `raced` faults: unclaimed faults on a page that another thread's fault had already opened again. They are retried and harmless; only the remainder are real unclaimed faults (logged as `[vm] unclaimed protection fault`).
- `RSX_AA_RESOLVE_MEMO` (default on; `0` = off) and `RSX_OBJMV_FAST_VHASH` (default on; `0` = off): cut the per-draw cost of the DLSS camera vote and object motion vectors. `RSX_AA_RESOLVE_MEMO` keeps the last 512 camera-matrix extractions (vertex program, branch bits and the exact constants it reads) and reuses a result when a later draw's inputs are byte-identical, for example the material pass after the depth pre-pass, or a camera that hasn't moved. The output is exactly the same. With `RSX_DLSS_OBJMV` on, the log prints `[aa] resolve memo: N hits, M misses` with the objmv2 line. `RSX_OBJMV_FAST_VHASH` hashes the same 16 sampled vertices per block 8 bytes at a time instead of byte by byte (about 4x faster). The hash is only compared with the previous frame's, so results can differ only on a 32-bit hash collision.
- `RSX_IBIND_SKIP` (default on; `0` = off) and `RSX_VPRUN_FAST` (default on; `0` = off; both were checked against the R2 hang of 2026-11-13 and are not on its path: the index-bind skip is reset every render pass and command buffer, and the interpreter records no GPU commands): two more exact RSX-thread fast paths shared with R2, output identical. `RSX_IBIND_SKIP` binds the renderer's index ring once per command buffer and render pass instead of before every draw, and passes each draw's start as its first index; the GPU reads the same indices from the same address (offline Vulkan harness `R2 scratch\rsx_native\dm_bench.cpp`: 0 differing colour/depth bytes, about 13 ns less per draw). `RSX_VPRUN_FAST` is a specialised version of the vertex-program interpreter that DLSS object motion vectors (`RSX_DLSS_OBJMV`) use to find each object's matrix: the same arithmetic in the same order, but only the operands an instruction reads are fetched (differential fuzz over 6 million random programs including NaN/infinity inputs: 0 differences; 1.75x faster). Both take the `[native]` switch values (`1`/`on`/`true`/`yes`, `0`/`off`/`false`/`no`) and are listed in the `[native]` line as `rsx-ibind-skip` and `rsx-vprun-fast`. With `R2_RSX_PROF=1` the `[r2rsx-prof]` memo line also counts the index binds left out; with `R2_RSX_CENSUS=1` an `r9 census draw-call reduction` line shows the share of draws that differ from the previous one only in constants, vertex base or index address, and the share with the same Vulkan state (counts only, nothing is merged). R3 draws fewer (about 1,100-1,500 per frame), so the gain is smaller than R2's 0.3 ms per frame, but a faster RSX thread also shortens the main thread's command-buffer drain wait.
- `RSX_ATEST_RESAMPLE` (default on; `0` = off): when the upscaler's alpha-test LOD bias (`RSX_AA_MIPBIAS_ATEST`) toggles, the fragment texture units the draw uses re-derive only their sampler from the unchanged descriptor instead of going back through the texture cache. The fallback is the old full re-upload, used for render-target sources, cyclic references, or after any invalidation. Output is identical. With `R2_RSX_PROF=1` the `RSX_SAMPLER_CACHE` line reports the re-uploads avoided per frame.
- `RSX_PIPE_MEMO_WAYS` (default 16; `1` = the old single-entry memo; `R2_PIPE_MEMO=0` turns the memo off): the pipeline memo keeps the last 16 pipeline-cache answers instead of one. A draw whose cache hint still names the same two programs, with identical pipeline properties, reuses the pipeline without the shader-cache lookup. Output is identical, because pipelines and programs live until the cache is cleared, and that also clears the memo.
- `RSX_AA_TEXREAD_MEMO` (default on; `0` = off): the upscaler's per-draw texture-read check computes the sampled addresses once for all of its checks, and its jittered-content check reuses the previous draw's answer when the draw samples the same addresses in the same frame and the set of jittered surfaces has not grown. Same result; `R2_RSX_PROF=1` prints the cost and the hits on a `resolve split` line.
- `RSX_TEX_SEARCH_MEMO_RANGE` (default on; `0` = off): the texture-search memo is invalidated per 1 MB storage block (the block that owns the looked-up address) instead of globally, so the uploads and faults of a busy outdoor frame no longer drop every memoised lookup. Results are unchanged.
- `RSX_TEX_SLOT_MEMO` (default `0` since round 11; `1` = on; `2` = validate): a front memo in `upload_texture` keyed by the raw texture-unit registers (offset, format, address, control1, image rect, control3) plus the resolved address. A repeat answers with the `RSX_TEX_SEARCH_MEMO` entry that hit for the same registers, re-running every check that hit makes (generations, section validity, `address_is_bound`, `sync_protection`), so the attribute derivation and memo hashing are skipped. Round 10 shipped it on; it was turned off after the purple / rainbow bullet-hole debris regression (unproven culprit, the perf win is small). Round-11 hardening: an entry also needs an unchanged global epoch (bumped by every invalidation, page fault, host DMA / blit write, flush, unprotect, purge, trim and cache-tag event), an unchanged surface-cache tag, and the same section lifetime serial and write tag (a reset, re-created, destroyed, dirtied or re-protected section never answers). `2` always takes the full path and compares the memo answer with it. A `[tex-slot-memo]` line every 5 s shows lookups/s, hit %, stores/s, validated/mismatch counts, self-checks and guard refusals.
- `RSX_TEX_SLOT_MEMO_CHECK` (default `64`; `0` = off): with `RSX_TEX_SLOT_MEMO=1`, 1 in N memo hits also runs the full path and compares. The first mismatch logs `[tex-slot-memo] self-check MISMATCH ... memo disabled for this session` and turns the memo off until exit.
- `RSX_OBJMV_ONEPASS_KEEP_DYN` (default `0` since round 11; `1` = the round-10 behaviour): after an object-motion onepass variant draw, keep the dynamic state and index binding instead of a full re-set at the next draw. Turned off with the moving-debris regression (unproven; tiny perf win).
- `RSX_PIPE_SPLIT` (default 0; `1` = on; `2` = on + validate): two-stage split of the per-draw r2aa work. Turns on the `RSX_RECORD_DEFER` lane (unless `RSX_RECORD_DEFER` is set) and moves a depth-writing objmv scene draw's loose key + ordinal and its transform-constant capture onto it, ahead of the classification; rsx::thread only snapshots the key words and the capture inputs. Exact: every r2aa entry point joins the lane first, and nothing writes the registers between `r2aa_on_draw` and the draw's own `pre_draw` join. `2` derives the expected loose key, ordinal and constant hash on rsx::thread and compares them at the join. A `[pipe-split]` line every 5 s (with the objmv2 line) shows draws/frame moved, us/frame moved off rsx::thread, stage-2 busy % and stalls. Vulkan recording is stage 2 via `RSX_RECORD_THREAD`.
- `RSX_SPLIT2` (default 0; `1` = on; `2` = on + validate): stage 2 of the r11 rsx::thread split (`VK\VKSplit2.h`). The transform-constant UBO fill of `load_program_env` (REGS -> mapped ring, ~2-3 KB per draw) runs on an ordered worker thread; rsx::thread still allocates, maps, windows and memoizes the range. Joins: before any queue submit (so before every label/report/flip/readback/texture-cache flush reaches the GPU), before any transform-constant write, before a ring heap is unmapped (grow/destroy) and at exit. `2` hashes the bytes the inline path would write at the kick and compares them with what the worker wrote. `RSX_SPLIT2_SPIN_US` (default 200) = worker spin before sleeping. `[split2]` line every 5 s: jobs/KB per frame, ms/frame moved, joins/stalls per frame by reason, ring-full stalls, validated/mismatches.
- `RSX_FIFO_HOOKS_FAST` (default on; `0` = off): the FIFO method loop tests all of its debug hooks (draw log, frame capture, draw flattener, feature coverage, profiler) with one combined branch per method and skips them together when none is active. With `R2_RSX_PROF=1` the profiler's FIFO counters are plain single-writer stores instead of locked atomics, and `R2_RSX_CENSUS=1` adds a per-register handler-time census and a housekeeping split (context, local tasks, zcull, labels, host DMA) to the RSX summary.
- `RSX_VK_PUSH_DESC` (default `0`; `1` = on, opt-in A/B): the game shaders' fragment descriptor set is pushed per draw with `VK_KHR_push_descriptor` instead of being allocated from a pool, written and bound. It needs device support and a set within `maxPushDescriptors` (otherwise the pool path is used), and it works with `RSX_DLSS_OBJMV=1` one-pass mode: the velocity variant re-pushes the draw's last fragment writes with its own layout instead of binding the set by handle (log `objmv onepass: N draws re-pushed their fragment descriptor set`; `RSX_VK_PUSH_DESC_ONEPASS=0` = old rule, push descriptors off with one-pass). A Fossilize cache recorded with it on skips those layouts when replayed with it off.
- `R2_DMA_INLINE_MAX=<bytes>`: renderer-thread change shared with R2, off by default since a 2026-11-11 R2 freeze report (opt-in): RSX DMA copies up to the given size run directly on the RSX thread instead of waking the Offloader thread (default `0` = the upstream 3.5 KB limit).
- **Aiming down sights (ADS):** the zoom depth-of-field pass (SPU job 419) reads back surfaces the RSX just rendered, and the main thread waits for that chain (`[r3-dof]`, `[ads-rb]` lines). The quickest way to normal-play frame rates while aiming is turning the blur off (*Aim-down-sights blur: Off*, `R3_FX_ADS_BLUR=0`). Fixes for keeping the blur (tested by users; the ones marked "default on" are on unless set to `0`, the rest are opt-in; compare the F3 overlay while aiming):
  - `RSX_ADS_STALE_OK` (**default off** since 2026-11-14; `=1` is opt-in and **can corrupt the image**): if the early GPU→host copy of a surface is still in flight when the SPU reads it, the SPU gets the previous readback instead of waiting (never twice in a row).
    - **The hazard:** the previous readback is written over the whole tiled region (about 5 MB from 0x30030000). That region also holds DOF job 419's in-place output and intermediate buffers, and the snapshot itself is copied while the job writes there. On about 6% of aimed frames in a user test, the composite then drew those bytes as the blur layer: the whole view went black with a low-res purple mosaic.
    - **Cost of the default:** with it off, the SPU waits for the copy instead, about 0.1–0.3 ms per aimed frame on average.
    - `RSX_ADS_STALE_ASYNC` (default on, but **only applies with `RSX_ADS_STALE_OK=1`**; `0` = off) takes that stale snapshot (another ~5 MB copy per hot flush) on a helper thread instead of the faulting SPU thread.
    - `RSX_ADS_FLUSH_DEDUP` (default on; `0` = off; exact): when one SPU fault flushes several sections of the same tiled region, bytes already copied from the DMA block are not copied again.
  - `RSX_ADS_KICK_AT_LABEL` (default on; `0` = off): start the early copy when the RSX releases the GCM label the SPU waits on, instead of when the surface is unbound or blitted (each surface learns its label; forgotten after 3 misses).
  - `R3_JOBWAIT_SPU_WAKE` (default on; `0` = off): the main thread's SPU-job wait sleeps until the job writes its result instead of polling; `R3_JOBWAIT_SPU_WAKE_US=<n>` is the fallback timer (default 2000). Missed wakes are counted in `[usleep-watch]`.
  - `R3_NATIVE_DOF_JOB=3`: the native DOF job (mode 2) plus a lean DMA path for its transfers; byte-identical output, about 0.05–0.2 ms per aimed frame. `R3_DOF_LEAN_DMA_OFF=1` keeps mode 3 on the full DMA path.
  - `R3_NATIVE_DOF_JOB=4` (the default; `0` = the lifted SPU code; a build without AVX2 keeps the lean / bulk DMA but not the native kernel loops): mode 3 plus bulk list DMA. A run of contiguous DMA-list elements of job 419 is moved with one range check and one copy. The per-element bookkeeping is kept, and anything unusual falls back to element by element. A unit test checks it is byte-identical. `[r3-dof] bulk list DMA` lines show it working; `R3_DOF_BULK_DMA_OFF=1` turns only this part off.
  - `RSX_ADS_KICK_ADAPT` (default on; needs `RSX_ADS_ASYNC_RB`): a DOF surface whose early GPU→host copies were not used by the SPU fault 3 flushes in a row stops being copied early (each copy is a ~5 MB load plus a GPU detile on the RSX thread). Every 32nd flush still copies it as a probe, and kicking resumes as soon as a copy is used. The copies are speculative, so the image is unchanged. The `[ads-rb]` line ends with `kick-adapt suppressed N`. To revert: `=0`.
  - `R3_DOF_FAST_SUBMIT` (default on; needs `R3_NATIVE_DOF_JOB>=3`): job 419's plain GET/PUT MFC commands skip the ~15 env-gated diagnostics in the MFC submit path. The repeat-poll bookkeeping, tag state and the (lean) transfer stay in the same order. It is not armed when any of those diagnostics is set (`[ndof] R3_DOF_FAST_SUBMIT: ... NOT armed (X set)`). A microbenchmark of the real DMA code measured 74 → 63 ns per DMA, with byte-identical results. To revert: `=0`.
  - `R3_DOF_GRAPHLOG=1` (diagnostic, off by default): logs the operation graph of DOF job 419 while aiming. `[dof-graph] new op#N` shows each distinct kernel call with its op block and per-frame parameters, `[dof-graph] seq` shows the call order, and the call counts are repeated every 5 s. `R3_DOF_HOSTJOB` turns it on too.
  - `R3_DOF_HOSTJOB=1` (diagnostic, off by default): shadow-verifies the host decode of the DOF job's step list. It is the first step towards a host/GPU DOF; `R3_DOF_GPU` is not implemented yet.
    - **How it works:** on sampled kernel calls it decodes each op (a small image such as 120×88, read from one buffer and written to another). It then checks that the input rows in guest memory are exactly what the kernel gets in its local store, and that the kernel's result is exactly what lands in the output buffer.
    - **Sampling:** the first `R3_DOF_HOSTJOB_VERIFY_N` calls (default 256), then every `R3_DOF_HOSTJOB_EVERY`-th call (default 64).
    - **It never replaces the SPU result.** The image is the same as without it, at a small cost on sampled calls.
    - **Log lines:**
      - `[dof-host] layout op#N … stride=… row=… (B/px)`: an op's data layout was learned.
      - `[dof-host] verify ok frame=… N get + M put checks matched`: every 5 s while it holds.
      - `[dof-host] unsupported op#N …`: the layout was not found; that op is left to the SPU path and logged once.
      - `[dof-host] verify FAIL op=… off=…`: a learned layout stopped matching. It is logged once and verification stops for the session.
    - **To revert:** `R3_DOF_HOSTJOB=0`.
  - `R3_DOF_GPU_APPROX` ("Aim blur: PC fast" in the launcher and in F10 > PC Options, next start; default on, `0` = "PS3 exact"): skips DOF job 419 and replaces it with a host approximation of its output, so the RSX no longer waits on label 77 for the SPU job. It is close to the PS3 look but **not pixel-identical**: same depth linearisation and CoC as the job, a 2×2 downsample and a separable 7-tap (20,15,6,1)/32 blur, composited by the CoC. Offline it scored 43 dB PSNR / SSIM 0.98 (ADS ramp, captured parameters) against a model of the PS3 blur. Host work is about 0.9 ms per aimed frame.
    - **Self-check:** it first lets the PS3 job run on probe frames and compares its output with the job's. The depth read must be byte-exact, and the job descriptor, parameter block, label value and sync-line end state must be consistent. The image is then judged on two numbers: how many CoC (alpha) bytes are within ±2 of the job's, and the PSNR of the final blended image.
      - Below 25% of CoC bytes within ±2: the output layout is wrong, and the probe fails.
      - 25–60%: passes only on a frame that blurs (≥ 5% of pixels) with PSNR ≥ 45 dB and ≥ `R3_DOF_GPU_APPROX_MINPSNR`. While the scope zooms in, the CoC moves frame to frame; the 2026-11-14 20:53 log failed PC fast for the session on such a frame (57.5% within ±2 at 59 dB, visually equal).
      - 60–90%: the final image must be visually equal on **every** probe frame, blurring or not: PSNR ≥ 35 dB and ≥ `R3_DOF_GPU_APPROX_MINPSNR`. The job's near-field mask term, which the approximation leaves out, shifts the CoC behind near objects; a 2026-11-14 test had 82.7% within ±2 at 69 dB.
      - 90% or more: PSNR ≥ `R3_DOF_GPU_APPROX_MINPSNR` (default 20 dB) on frames that blur.
    - **Arming:** it arms after 3 good probes, one of them blurring, and re-probes every `R3_DOF_GPU_APPROX_RECHECK` frames (default 3600, was 900; 0 = never; each re-probe frame runs the full PS3 job, a short hitch). Probes are judged with the parameter block as it was at job entry; a probe whose block the game rewrote while the job ran is not counted. Probe lines also show the mean CoC byte difference (`mean |dA|`). Zoom-ramp and CoC-settling probes are not counted and no longer reset the good-probe count (`R3_DOF_FAST_RAMP_KEEP`, default on; `0` = a settling probe resets it, the old rule that kept the first ADS on the PS3 path for the whole zoom-in).
    - **Arming cache (`R3_DOF_FAST_CACHE`, default on; `0` off):** the probe phase runs job 419 on the PS3 path (light-buffer readback fault, game thread waiting 15–40 ms on the SPU job list), so the first ADS of a session ran at ~25 fps for 1–2 s. An arming is saved to `r3_dof_fast.cache` next to the exe (stamped with the exe's build, so a rebuilt or updated exe ignores an old file); the next session arms from it on the first job 419 frame (or the second, if kernel 618's block moved) once the job entry, geometry, parameter block, sync line and region match it live. The cached sync-line rule and label value are checked on the next armed frames and on every re-probe; any mismatch or failed probe deletes the cache and goes back to probing. The first fast frame has no earlier output to hold, so black or FP16-garbled input there gives the neutral output (`R3_DOF_FIRST_USE_GUARD`). Log: `[dof-fast] ARMED from R3_DOF_FAST_CACHE …` and, once per session, `[dof-fast] first ADS: first PC fast frame at serial … after X ms / N frames: M job 419 frames ran on the PS3 path before it (P probes) -> armed from R3_DOF_FAST_CACHE | armed by probes`.
    - **Armed frames:** kernel 618's per-frame block must hold this frame's serial or the previous frame's (the game writes it after the job starts). While armed the job is skipped, so only a fresh block says what this frame's image is: a stale one makes that frame use the PS3 job. A fresh block with another image size, depth column or tile bank (a resolution change) drops back to learning: the PS3 job runs and probes the new geometry before PC fast runs again (log: `… probed WxH … -> PS3 exact aim blur, probing the new geometry`).
    - **Fallback:** a failed image probe resets the count, uses the PS3 job and probes again `R3_DOF_GPU_APPROX_RETRY` frames later (default 60, 0 = next frame). After `R3_DOF_GPU_APPROX_MAXFAIL` failed probes without an arming in between (default 10; `1` = the old first-failure-is-final behaviour) it is off for the session. Inconsistent descriptors, labels, sync-line state or input images still switch it off for the session. A frame whose parameter block or image memory cannot be read uses the PS3 job for that frame.
    - **GPU path (`R3_DOF_GPU`, default on):** armed frames are computed by the RSX. Before the CPU work is skipped, one GPU frame is compared with the CPU path (PSNR ≥ `R3_DOF_GPU_MINPSNR`, default 30 dB). The comparison frame must use its own kernel 618 block (not a `R3_DOF_FAST_BLOCK_STALE` neighbour) and the DOF parameters must not have ramped within `R3_DOF_GPU_CHECK_RAMP_HOLD` frames (default 4, so the check also comes while firing); until then frames stay on the CPU fast path. If `R3_DOF_GPU_CHECK_STALE` consecutive armed frames (default 15; `0` = own block only) bring only a neighbour's block, as in the diner, a settled stale-block frame is compared instead. A failed check runs the CPU fast path and checks again `R3_DOF_GPU_CHECK_RETRY` frames later (default 300); the GPU path is off for the session after `R3_DOF_GPU_CHECK_MAXFAIL` failed checks (default 3; `1` = the old first-failure-is-final behaviour) or `R3_DOF_GPU_MAXMISS` unserved requests.
     - **Black-frame guards (CPU fast path):** `R3_DOF_FAST_RSX_GATE` (default on) reads the light buffer only after the RSX processed label 77's reset release (its input blits), waiting at most `R3_DOF_FAST_RSX_GATE_MS` (default 20); five timeouts in a row turn it off. `R3_DOF_FAST_BLACK_HOLD` (default on) shows the last good aim-blur output when the input is black, is FP16 lighting data read as colour (purple with vertical comb stripes), or was read after a gate timeout, right after a clean frame (at most 2 frames). Both fix the black and purple ADS frames while firing.
      - **First-ADS guard:** `R3_DOF_FIRST_USE_GUARD` (default on; `=0` off) covers the first ADS of a session, when job 419 still runs on the PS3 path for its probe frames (and again on each `R3_DOF_GPU_APPROX_RECHECK` probe). It also covers the first fast-path frame, which has no earlier good output to hold. Right before such a job stores label 77, its output is checked. If the input is FP16-garbled or black, or the CoC is saturated on every pixel (garbage depth), the output is replaced with a neutral one (A = 0, so the composite shows the sharp scene) and the probe is not counted. This fixes the one-off purple full-screen frames on the first ADS while firing. The fast-path part needs `R3_DOF_FAST_BLACK_HOLD`.
    - **Log lines:** `[dof-fast] probe … -> ok/FAIL/SKIP (zoom ramp | CoC settling, not counted)`, `[dof-fast] probe FAIL (why, n of max) -> PS3 exact aim blur, probing again in N frames`, `[dof-fast] probe … not counted`, `[dof-fast] armed after N good probe frames`, `[dof-fast] N frames on the PC fast path, host work avg X ms` (every 10 s), `[dof-fast] … -> PS3 exact aim blur (job 419) for the session`.
    - **To revert:** `R3_DOF_GPU_APPROX=0` (or Aim blur: PS3 exact).

Not done, and why:
- **Large pages for guest memory:** guest memory is committed lazily on fault, and the RPCS3 texture cache write-protects single 4 KB pages. Neither works on 2 MB pages. Large pages also need the *Lock pages in memory* right.
- **Running SPU jobs in parallel:** jobs in a list run in order and share data.

**CPU target:** The normal `build.bat` build compiles the lifted PPU/SPU code for x86-64-v3 (AVX2, FMA, BMI2: Intel 4th gen / AMD Ryzen or newer) and the runtime and hand-written code for x86-64 + SSE4.1 (CMake `PORT_ARCH=mixed`, the default). FMA contraction is off everywhere (`-ffp-contract=off`), so the lifted float results match the PS3's separate multiply and add. At start the exe checks the CPU and, on one without AVX2, shows "This build cannot run on this processor" with the hint to build the variant without AVX2 instead of crashing (on a CPU without SSE4.1, which no build supports, it says the processor is below the minimum instead; `PORT_CPU_CHECK=OFF` drops the check). `build_cpu.bat baseline` builds the variant without AVX (x86-64 + SSE4.1, `PORT_ARCH=baseline`; its start-up check asks for SSE3, SSSE3 and SSE4.1) into `build_baseline\`; setup builds it by itself on a CPU without AVX2 that has SSE4.1, and the launcher then starts it (`PORT_CPU_V3=0`). `build_cpu.bat` (`PORT_ARCH=AVX2`) also builds the runtime and hand-written code for x86-64-v3.

**Renderer (rpcs3_rsx) code generation:** `build.bat` builds the RPCS3 renderer library with `/GS- /Gw`, `-march=x86-64-v3 -mno-fma` (AVX2 without FMA; the exe already needs AVX2) and ThinLTO (`-flto=thin`); the runtime and hand-written code get `/GS- /Gw` too (CMake `PORT_GS_OFF`). `/fp:precise` stays. Without LTO these produce exactly the float results of the old generic build: `-mno-fma` keeps clang-cl's `a*b+c` contraction folded fused at compile time and run as a separate multiply and add at run time. **ThinLTO and PGO builds of the renderer have the same semantics as /O2 with `-ffp-contract=on`, but are not guaranteed bit-identical** to the non-LTO build: a cross-file inline that turns an `a*b+c` into constants is folded fused, where the non-LTO build computed it unfused (a probe showed 1.49e-8 vs 0). port_dlss_quality's tests pass through the ThinLTO link. For a strictly identical renderer, `set PORT_RSX_LTO=0` before `build.bat` (and do not use the PGO builds); `set PORT_RSX_ARCH=generic` restores the old CPU target. `build_cpu.bat` builds a matching renderer per mode (`build_rpcs3_generic`, `build_rpcs3_pgo_gen`, `build_rpcs3_pgo_use`).

**Builds**: each build goes into its own folder, and `build.bat` is unchanged. `run.bat` runs `PORT_GAME_EXE` when it is set, for example `set PORT_GAME_EXE=build_cpu\Resistance3.exe`.

| Command | Output | Notes |
|---|---|---|
| `build_cpu.bat` | `build_cpu\Resistance3.exe` | AVX2 for the runtime and hand-written code, plus ThinLTO (`-flto=thin`; the toolchain is clang-cl, so `/GL` and `/LTCG` don't apply). The lifted PPU objects are reused from `build\`. |
| `build_cpu.bat baseline` | `build_baseline\Resistance3.exe` | No AVX (x86-64 + SSE4.1; setup builds it by itself on a CPU without AVX2 that has SSE4.1). The launcher's CPU check selects it on CPUs without AVX2 (`PORT_CPU_V3=0`). |
| `build_cpu.bat tracy` | `build_tracy\Resistance3.exe` | [Tracy](https://github.com/wolfpld/tracy) zones from a Tracy v0.15 source checkout (`set PORT_TRACY_DIR=<folder>` before `build_cpu.bat tracy`; no default). Connect the Tracy 0.15 viewer while the game runs; nothing is recorded until it connects. Zones: `syscall` / `hle` (each guest syscall or HLE import), `spu job` / `spu wait` (each SPU job and blocking channel wait), `spin` (each `r3_spin_relax` wait, merged from its laps), and `RSX flip` frame marks. Tracy's crash handler is off, because the port's exception handler commits guest memory. |

**PGO**:
1. Run `build_cpu.bat pgo-gen`.
2. Run `tools\pgo_train.bat` and play for 10–20 minutes, covering heavy fights, a level load, a checkpoint reload, cutscenes and menus.
3. Run `tools\pgo_merge.bat`. It writes `pgo\r3.profdata`.
4. Run `build_cpu.bat pgo-use`. It builds `build_pgo\Resistance3.exe`.

`scripts\pgo_build_instrumented.ps1` (step 1) and `scripts\pgo_merge_and_build.ps1` (steps 3 and 4) do the same under the build lock; the latter cleans `build_pgo` and `build_rpcs3_pgo_use` when the merged profile changes. The renderer is profiled too. Every PGO object depends on the `.profdata` file, so a new profile recompiles them.

**PGO in the normal build:** when `pgo\r3.profdata` exists (it is committed once the maintainer has recorded it), `build.bat` optimises the renderer, the runtime, the hand-written and the lifted SPU code with it automatically and prints `PGO: optimising with pgo\r3.profdata`. The profile is LLVM indexed profile format 13, so it needs **LLVM (clang-cl) 22 or newer**: Setup installs or updates LLVM to that, and `build.bat` stops with a clear message on an older clang-cl (`build.bat nopgo` builds without the profile). Opt out with `set PORT_PGO=0` or `build.bat nopgo`. A profile older than the sources is fine: functions that changed since it was recorded are built without profile data (the out-of-date/unprofiled warnings are switched off), the rest keeps the gain. The profile keys do not depend on the folder the port is in, except for C++ functions in anonymous namespaces (about 1% of the profiled run time), which only get profile data when the port is built at the same path as the training build. To record or refresh it: run steps 1–3 above (`scripts\pgo_build_instrumented.ps1`, `tools\pgo_train.bat`, `scripts\pgo_merge_and_build.ps1`), then commit `pgo\r3.profdata`.


The CMake options behind these are `PORT_ARCH`, `PORT_CPU_CHECK`, `PORT_LTO`, `PORT_LTO_PPU`, `PORT_PGO`, `PORT_PGO_PROFILE`, `PORT_PGO_PPU`, `PORT_PPU_PREBUILT_OBJ_DIR`, `PORT_SPU_INLINE_CH`, `PORT_TRACY` and `PORT_TRACY_DIR`.

### GoW Ascension adoptions

Switches taken from the MIT-licensed God of War: Ascension recomp (see `THIRD_PARTY_NOTICES.md`). Each can be set back to the old behaviour.

| Variable | Default | Effect |
|---|---|---|
| `GCM_PUT_ORDER` | `2` | Shared with all three ports, after the GoW Ascension recomp (3 freezes in 17 runs → 0 in 41 there). `2`: an SPU DMA PUT into the GCM command buffer writes the block's park/JUMP word last, so the RSX never follows a jump into a half-written block. `1`: ascending order. `0`: the old single `memcpy`. |
| `GCM_PARK_WAIT_MS` | `50` | How long the GCM FIFO walker waits on a self-JUMP park whose word has not been patched yet before following `put` (which skips the parked commands). Raise it (e.g. `2000`) if a slow CPU freezes on a frame label; `50` is the old fixed grace. R2 / R3 use RPCS3's FIFO, which already waits on the park. |
| `SPURS_PRIO_SKIP_SAME` | `1` | `cellSpursSetPriorities` returns early when the priorities are unchanged (GoW: roughly half the watchdog CPU). `0` = always reapply (old behaviour). |
| `PAD_SQUIRCLE` | `4000` | Maps the round host stick onto the PS3's square stick range so diagonals reach the corners (squareness ×1000; `0` = old per-axis mapping). The centre stays exactly 128. |
| `PAD_MERGE` | `0` | `1`: every connected controller drives player 1 (buttons OR'd, each stick follows the controller that deflects it most). Off by default because of local co-op. |
| `RSX_ZBIAS_D32` | auto | Polygon-offset constant on GPUs without a 24-bit depth format (AMD: RPCS3 falls back to 32-bit float depth, where Vulkan's bias unit shrinks with the depth value, so shadows and decals far from the far plane get almost no bias). Auto: on only when that fallback is active; the constant goes into the vertex shader's viewport z (bias/16777215, exact like the PS3's 24-bit depth) and only the slope stays in the GPU depth bias. `0` = off (upstream), `1` = on for every 24-bit fixed depth surface. |


## Audio

When the frame rate drops, the game's own audio mixing (on the recompiled PPU/SPU threads) can fall behind real time. The port therefore keeps a buffer of mixed audio between the game and the sound card, as RPCS3 does with its "audio buffering" and "time stretching" options:

- **Buffer:** mixed audio goes into a ring buffer with a target of `PORT_AUDIO_BUFFER_MS` (100 ms by default). The sound card is kept topped up from it, about 30 ms at a time.
- **Time stretching:** when the buffer drops below `PORT_AUDIO_STRETCH_THRESHOLD` % of the target, playback slows down through [SoundTouch](https://www.surina.net/soundtouch/) without changing the pitch, so a slow stretch of frames sounds slightly slower instead of gapping. Tempo returns to 1.0 as the buffer refills.
- **Underrun:** if the buffer still runs dry (a hitch longer than the buffer), the last few milliseconds fade out to silence and fade back in when audio returns. No repeated blocks, no clicks.
- **Mixer thread:** runs at TIME_CRITICAL priority with Windows MMCSS "Pro Audio" scheduling. It also stays off the cores reserved for the main game thread, the RSX thread and rawSPU0 (`PORT_MAIN_CPU`, `PORT_FIFO_CPU`, `PORT_SPU0_CPU`).
- **Late game audio:** when the game's next block of audio has not been written in time, the mixer waits up to `PORT_AUDIO_LATE_WAIT_MS` (22 ms) for it. The game's audio clock slips slightly and the buffer absorbs the slip.

| Variable | Default | Effect |
|---|---|---|
| `PORT_AUDIO_STRETCH` | `1` | SoundTouch buffer and time stretching. `0` = the previous audio output path, unchanged (the older built-in WSOLA stretcher; `PORT_AUDIO_WSOLA=0` turns that off too). |
| `PORT_AUDIO_BUFFER_MS` | `100` (`150` with fewer than 12 logical CPUs) | Target buffer, 20–500 ms. More = fewer underruns, more latency. |
| `PORT_AUDIO_STRETCH_THRESHOLD` | `75` | Stretch below this % of the target buffer. |
| `PORT_AUDIO_STRETCH_MIN` | `0.5` | Slowest tempo while stretching (0.1–1). |
| `PORT_AUDIO_FADE_MS` | `5` | Fade-out / fade-in length on an underrun. |
| `PORT_AUDIO_DEVICE_MS` | `30` | Audio handed to the sound card at once. |
| `PORT_AUDIO_CPU` | – | Pin the mixer thread to one logical CPU; `-1` leaves its affinity alone. |
| `PORT_AUDIO_MMCSS` | `1` | `0` = no MMCSS "Pro Audio" scheduling for the mixer thread. |
| `PORT_AUDIO_LATE_WAIT_MS` | `22` | Longest wait for a late block of game audio (0–40, `0` = off). |
| `PORT_AUDIO_LATE_KEEP_PCT` | stretch threshold + 15 (`90`) | The late-block wait never takes the buffer below this % of the target, so a run of late blocks (heavy scenes, aiming with an expensive upscaler) is concealed instead of slowing the sound to ~0.5x. `0` = the old 4-block floor. |
| `PORT_AUDIO_PAUSE_FREEZE` | `1` | While the game is paused (PC menu, window in the background) the game's audio clock stops: silence, no block consumed. `0` = the old behaviour. |
| `PORT_AUDIO_STALL_FREEZE_MS` | `150` | The same hold when the game stalls without pausing (after an alt-tab the renderer may rebuild the swap chain and upscaler, ~2.4 s with XeSS): held while no frame has completed **and** the game's audio has been missing for that many ms; released on the next frame or after 3 s. A frame hitch alone, with the audio still arriving, is not held. `0` = off. |
| `PORT_AUDIO_FOCUS_REPRIME` | `1` | `0` = off. On: when the window regains focus (alt-tab back), or after the game's audio was held for at least `PORT_AUDIO_REPRIME_HOLD_MS` (default `500`), restart the output stage. The leftover buffer and the slowed tempo are dropped, and it re-primes to the target with fresh audio, costing about one buffer of silence. Regaining focus always checks the output device immediately, instead of up to 1 s later. |
| `PORT_AUDIO_DRIFT` | `1` | Smooth clock-drift steering: the game's audio clock is nudged (at most `AUDIO_CATCHUP_PCT`, 3 %) so the buffer settles on the target even when the sound card's clock runs slightly fast or slow. The estimate is in the 10 s line (`clock drift +NN ppm`). `0` = the old on/off catch-up. |
| `PORT_AUDIO_ADAPTIVE` | `1` | A 10 s window with an underrun or more than 2 % stretching raises the target buffer by 25 ms, up to `PORT_AUDIO_BUFFER_MAX_MS`; 5 clean minutes step it back down. `0` = fixed target. |
| `PORT_AUDIO_BUFFER_MAX_MS` | `300` | Ceiling for `PORT_AUDIO_ADAPTIVE` (up to 500). |
| `PORT_AUDIO_UNDERRUN_LOG` | `1` | Every 10 s: `[audio] underruns N in last 10 s ... session: N underruns | clock drift ...`. `0` = off. |
| `PORT_AUDIO_ELASTIC` | `0` | Experimental, after the GoW Ascension recomp's `AUDIO_ELASTIC`. `1`: when a block of game audio is late, the mixer waits for it while the buffer stays above 90 % of the target, then plays a short fade to silence *without* skipping the game's block, which plays when it arrives; the time lost is made up later on silent blocks. Replaces the late-block wait (and the read delay). Log: `[audio] elastic 10 s: ...`. |
| `PORT_AUDIO_ELASTIC_CAP_MS` | `150` | With `PORT_AUDIO_ELASTIC=1`: a port with no block for this long is treated as stopped (no more waiting for it). |
| `PORT_AUDIO_ELASTIC_DEBT` | `8` | With `PORT_AUDIO_ELASTIC=1`: most concealed blocks to make up later; beyond this they are forgiven. |
| `PS3_LANG_VOICE_FALLBACK` | `1` | English (UK) (Windows set to English (United Kingdom), or `PS3_LANG=en-GB`) has no voice-over on the disc: cutscenes and speech play the English voice-over and the UK text is kept. Another language gets the English voice only when the disc has no dub for it at all (checked once over the speech movies; log: `[lang] system language N: no voice-over on this disc ...`). A dubbed language keeps a movie that lacks its track as it was rather than switch to English mid-game. `2` = also replace the language in any single movie or speech file that lacks it. `0` = off (the game asks for the missing UK track and plays no dialogue). |
| `PORT_AUDIO_LOG` | `5000` | Period of the `[audio]` log line in ms. `1` = every second (also with `R2_RSX_PROF=1`), `0` = off. |
| `PS3_THREAD_SLOT_FIX` | `1` | Shared with the R1 / R2 ports: a thread that ended through `sys_ppu_thread_exit` while another thread was already waiting to join it could keep its slot in the 64-entry thread table for good, until thread creates failed and the game waited for a thread that never started (R1 issue #17: black screen after a cutscene). A refused thread create is now logged (`[SYS] sys_ppu_thread_create ... FAILED: all 64 thread slots in use`). `0` = the old behaviour. |

**Reading the log.** At start-up, `logs\run.log` shows `[audio] output: ... SoundTouch stretch (...)` with the MMCSS state and the mixer thread's affinity. Every 5 seconds there is a line like:

```
[audio] 5.0 s: buffer min 82 avg 101 ms (target 100) | tempo min 1.00 avg 1.000 (stretched 0%) | underruns 0 (silence 0 ms, device dry 0) | ...
```

- `buffer min` well above 0 and `avg` near the target: healthy.
- `tempo min`/`avg` below 1.00 and `stretched` above 0 % during a frame-rate drop: the stretcher is covering it. Tempo should be back to 1.000 within a second or two.
- `underruns` and `device dry` should stay at 0. A non-zero count means a hitch longer than the buffer; try a larger `PORT_AUDIO_BUFFER_MS`.
- `ring overflow` at the end: the game produced audio faster than it was played, so the oldest audio was dropped (harmless after a long pause).

The offline test for this stage is `ps3recomp\libs\audio\tests\test_audio_out.cpp` (part of `scratch\enginetest\run_all.ps1`).

## Steam Deck / Linux

The port is a Windows program. On Linux and the Steam Deck it runs through Proton (Wine). This has not been tested on a real Deck yet, so treat it as experimental.

1. Build the port, either on Linux itself with `setup_linux.sh` (see [Building on Linux](#building-on-linux-experimental) below), or on a Windows PC with Setup (no file picker is needed: the installer and Setup find the game on their own, or take a typed path). If you built it on another PC, copy the whole port folder to the Deck, for example to `/home/deck/Games/Resistance3Port` (or a microSD card). Setup.exe / Setup.bat themselves do not run under Wine or Proton (they need Windows PowerShell and Visual Studio).
2. In Desktop Mode, open Steam → **Games → Add a Non-Steam Game to My Library…**, click **Browse**, and pick `Launcher.exe` in the port folder.
3. Right-click the new entry → **Properties → Compatibility** → tick **Force the use of a specific Steam Play compatibility tool** and choose **Proton Experimental** (or Proton 9.0 or newer).
4. Launch options are not needed. `SteamDeck=1 %command%` forces the Deck preset on other Linux PCs.

What the port does under Proton:

- The launcher detects Proton and the Deck (its hardware line says `Steam Deck` or `Wine / Proton`). On the Deck, **Auto-detect** picks a Deck preset: PS3 resolution, FSR 1 scaling to a 1280x800 window, 30 fps.
- **Preset: Steam Deck** (launcher, the *Recommended for your PC* panel): battery-friendly handheld settings on any PC — the Deck recommendation (PS3 resolution, FSR), **40 fps** (set the Deck's screen to 40 Hz), 30 fps menus, a 1280 x 800 window, 150 % UI scale and Xbox button prompts. The Deck is detected by `SteamDeck=1` (set by Steam), the APU name, or (Windows on a Deck) the SMBIOS board name `Jupiter` / `Galileo`; there the 40 fps / 1280 x 800 choices appear and 1280 x 800, 150 % UI and Xbox prompts become the defaults.
- The frame rate list gets a **40** option. Set the Deck's screen to 40 Hz (Quick Access → Performance) to match it. The window list gets **1280 x 800** (the Deck's screen).
- DLSS is not used under Proton; choose FSR instead. The Vulkan renderer runs on the Deck's own Vulkan driver.
- In the launcher, the controller's **A** or **Start** button starts the game. In game, Steam Input presents the Deck's controls as an Xbox controller.
- The update check works the same way and can be turned off in the launcher.

### Building on Linux (experimental)

`setup_linux.sh` does what Setup does, natively on Linux and without PowerShell: it checks and copies your game, decrypts the program file, generates the game code, downloads and patches RPCS3's renderer source (with git) and builds the same Windows programs with LLVM (clang-cl and lld-link). The Windows headers and libraries (Microsoft's C runtime and the Windows SDK) are downloaded from Microsoft with [xwin](https://github.com/Jake-Shadle/xwin) into `tools_cache/msvc_linux`, after you accept Microsoft's licence. You then play the result through Proton as described above. It has been checked less than the Windows setup, so please report problems with `logs/setup_linux.log`.

1. Install the tools (LLVM 22 or newer is recommended; with older LLVM the PGO profile is skipped and the game runs a bit slower):
   - Arch: `sudo pacman -S --needed python cmake ninja clang lld llvm git curl 7zip`
   - Fedora: `sudo dnf install python3 cmake ninja-build clang lld llvm git curl 7zip`
   - Debian / Ubuntu: `sudo apt install python3 python3-venv cmake ninja-build clang lld llvm git curl 7zip` (LLVM 22 from [apt.llvm.org](https://apt.llvm.org) if your release has an older one)
2. Get the port (git clone or the source zip) into a folder with about 50 GB free, then run:
   ```
   ./setup_linux.sh --game "/path/to/Resistance 3 [BCUS98176].iso"
   ```
   `--game` takes a decrypted .iso or a folder with `PS3_GAME` in it (for example from RPCS3's `games` folder). UDF disc images are unpacked with 7-Zip. Other options: `--jobs N` (fewer compile jobs if you have little RAM: 16 GB → 4, 8 GB → 2), `--check-only`, `--nopgo`; `./setup_linux.sh --help` lists them all.
3. Later rebuilds (after `git pull`): run `./setup_linux.sh` again (it regenerates the game code only when the code generator changed), or `./build_linux.sh` for a build only.

Steam Deck: SteamOS's system folders are read-only, so install the tools inside a [distrobox](https://distrobox.it/) container (for example Arch) and run `setup_linux.sh` there, or build on another Linux PC and copy the folder over. The build takes a long time on the Deck's 4 cores.

Not on Linux: NVIDIA DLSS / DLSS Frame Generation and Intel XeSS are not set up (Proton does not offer DLSS to the port; FSR 3.1 is used), and the launcher's **Update now** is not offered under Proton (the updater is a Windows PowerShell script): update with `git pull` and `./setup_linux.sh`, or the new release's source.

## Status

This is a work in progress, tested on a single PC.

- Runs at about 52–60 fps in Haven on my PC (CPU-bound; the GPU is at ~40%).
- Performance is mostly limited by the game's SPU job system, so a decent CPU helps most.
- There are occasional freezes and other bugs.

If you hit a problem, let me know how to reproduce it, and if you can, send the log from the `logs\` folder for that session (the launcher has a button for it). That helps a ton.

## Known issues

- **DLSS is experimental.** Some textures can still shuffle or shimmer, and dark patches can appear on some surfaces. If they bother you, use AMD FSR 3.1.
- **Aiming down sights and some heavy fights can slow down** (the game is CPU-bound there). Please send `logs\run.log` if you see it.
- **Frame Generation is experimental and barely tested** (DLSS on RTX 40/50, FSR 3 elsewhere; off by default). Expect ghosting, jitter on grass / vegetation and around doors and entrances, and HUD or menu artifacts; fixes are coming in an upcoming hot patch, and reports are welcome.
- **Changing Frame Generation in-game** can double the sound and then leave constant static. Change it in the launcher, or restart the game after changing it.
- **Occasional microstutter**, even with a complete shader cache. The `[hitch]` lines in `logs\run.log` help.
- Ultrawide (21:9 / 32:9), the shadow-safe FOV and LOD distance are new and untested in game; ultrawide needs the Compatible renderer. Report black bands, missing shadows at the screen edges or a wrong aim zoom.
- 60 fps and above change the game's timing; if something (physics, a scripted sequence) looks wrong, try 30 fps in the launcher. 120 fps and above are less tested than 60.
- Exclusive fullscreen can give black F12 screenshots; use borderless.
- Occasional freezes or crashes are possible, especially past the opening level.

## How it works

- `ps3recomp/` is a modified copy of [ps3recomp](https://github.com/sp00nznet/ps3recomp) by sp00nznet (MIT licence). It holds the runtime, the PS3 system libraries (audio, input, file system, SPU scheduling) and the lifters that translate PowerPC and SPU code into C/C++.
- Graphics: the game's RSX command stream is fed to RPCS3's RSX core and Vulkan renderer, built as a library. This repository only contains the patch to RPCS3 (`ps3recomp/patches/r3-rpcs3.patch`); Setup downloads the original source and applies it. The patch adds DLSS / FSR upscaling, display modes and fixes for running outside the emulator.
- `project/` is the game-specific part of the port: its hooks, the frame limiter, mouse look, button prompts, the RPCS3 patches (`r3_patches.cpp`), the PC features (`r3_pcport.cpp`: quit box, screenshots, focus pause), crash reports (`r3_crash.inc`), the launcher and the DLSS bridge.
- `tools/art/make_r3_art.py` draws the launcher's and the game's icons and the launcher artwork (Python + Pillow).
- `tools/r3_regen.py` runs the lifters on your decrypted `EBOOT.elf`, then re-applies this port's own edits to the generated code (`tools/hooks/`).

## GPU offload switches

Graphics work runs on the GPU and game logic runs on the CPU. At startup the game prints one `[gpu-offload] <name> ON` line for each GPU path that is active.

| Variable | Default | What it does |
|----------|---------|--------------|
| `RSX_GPU_TEXDECODE` | 1 | Texture deswizzle/byteswap runs in a compute shader (images of 1 KB and up). Set 0 to decode on the CPU. |
| `RSX_TEXDECODE_LINEAR_CPU` | 1 | Linear (non-swizzled) textures byteswap on the CPU even when `RSX_GPU_TEXDECODE` is on. Set 0 to send them through the compute shader too. |
| `RSX_GPU_BLIT` | 0 | Scales blits on the GPU (RPCS3 "GPU texture scaling"). |
| `RSX_GPU_TEXSTREAM` | 0 | Uploads textures on an asynchronous streaming queue. |
| `RSX_RECORD_THREAD` | 0 | Experimental. `1` = the RSX thread captures its Vulkan draw commands (vkCmd* calls and descriptor updates) into a ring and an "rsx record" thread records them into the command buffer. Command-buffer begin/end/submit, object destruction, descriptor pool resets, the flip and the upscaler drain the ring first. `2` = validation: same capture path, replayed on the RSX thread (no second thread). |
| `RSX_RECORD_RING_MB` | 16 | Size of the record ring (2-256 MB). |
| `RSX_RECORD_SPIN_US` | 250 | How long the record thread spins for new commands before it sleeps. |
| `RSX_RECORD_STATS` | 1 | With `RSX_RECORD_THREAD` set, prints a `[rec]` line every 5 s: packets, fallbacks, drains by reason, ring stalls and record-thread busy %. `0` = off. |

Vertex fetch (vertex shader) and tiled-surface detile (compute) are always on the GPU.
